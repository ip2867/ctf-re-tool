# 复盘报告：为什么跑了 2 小时没解出来

> 数据来源：`cases/elfstudy_a6f6829f/`（findings.json + timeline.jsonl，500 个事件）
> 和本轮对照实验。所有数字都是实测，不是估计。

---

## 一、事实：那次到底发生了什么

```
2026-10-31 03:09:25  开始
2026-10-31 05:08:38  结束
```

- **历时 1 小时 59 分**
- **500 个事件**，其中 194 个 success、32 个 warning、2 个 error
- **零 flag**

关键节点：

| 时间 | 事件 |
|---|---|
| 03:09:48 | `[IDA] 越界地址 44/159 个不在映像内（ImageBase=0x0, SizeOfImage=0x1b330）` |
| 03:09:50 | `[花指令探测] 跳转目标非对齐 39/7530（0.52%） ⚠ 高度可疑` |
| 03:10:14 | `AI分析失败: [403] request illegal` |
| 03:50:18 | 快速模型未出 flag，升级思考模型 |
| 03:51:32 | 阶段 2.5 Tool-Use 深度求解开始 |
| 04:01:00 | 深度求解完成，耗时 568 秒；`本地枚举候选全部无效` |
| 04:22:35 | 阶段 2.5 **第二次**开始（提示词里又是「未发现算法指纹」） |
| 04:26:48 | 阶段 2.5 **第三次**开始 |
| 05:08:38 | 深度求解耗时 2510 秒后 `AI 请求失败: aborted` |

而 AI 最终写进 `findings.json` 的结论是：

> 花指令导致 39 处跳转目标落在指令边界外，当前 IDA 反编译整体错位
> （`.init_proc` 之后全是 0xe 字节的碎函数就是证据）。按硬性禁令，修前不能下算法结论。

**这个结论是错的。** elfstudy 里根本没有花指令。它是 ELF 加载期自解密题。

## 二、根因：一个信噪比为 0 的告警

`src/js/app.js:9553` 和 `electron/main.js:3795`：

```js
suspicious: bad >= 20 || ratio > 0.002
```

`ratio > 0.002` = **0.2% 就判「高度可疑」**。

我拿 8 个文件实测了这个阈值：

| 文件 | badTargets | insnCount | ratio | 旧阈值判定 |
|---|---|---|---|---|
| license（题） | 4451 | 386519 | **1.152%** | ⚠ 高度可疑 |
| fw_a（题） | 1865 | 249983 | **0.746%** | ⚠ 高度可疑 |
| elfstudy（题） | 39 | 7530 | **0.518%** | ⚠ 高度可疑 |
| msvcrt.dll | 290 | 221919 | 0.131% | ⚠ 高度可疑 |
| user32.dll | 264 | 319301 | 0.083% | ⚠ 高度可疑 |
| ntdll.dll | 378 | 628063 | 0.060% | ⚠ 高度可疑 |
| notepad.exe | 23 | 68524 | 0.034% | ⚠ 高度可疑 |
| kernel32.dll | 77 | 234802 | 0.033% | ⚠ 高度可疑 |

**微软官方的 ntdll.dll、kernel32.dll、notepad.exe 全被判「高度可疑」。**

这个告警的**信噪比是 0**：对每一个正常程序都误报。它在 elfstudy 上触发，不是"发现了线索"，是**必然触发**。

而它触发后的后果非常严重——`app.js:9554` 会往提示词里注入一整段：

```
## ⚠ 花指令检测：本题高度可疑（必须处理）
```

配上"必须处理"这四个字，AI 自然会走花指令修复的路。**工具用一条必然误报的告警，把 AI 推向了错误方向。**

## 三、连锁失效：一条错误告警如何放大成 2 小时

### 3.1 第一步：错误告警抢占了「主线」

`scan_crypto` 的正确结论是：

```
【(未发现算法指纹)】fingerprints=0 payloads=0 highEntropy=8
```

注意 `highEntropy=8`——工具**确实看到了 8 块高熵数据**（其中就包括 0x7396 的密文）。
但它没有把"高熵块"和"页尾缝隙"联系起来，因为那个时候**根本没有 ELF 结构检测**。

于是 AI 手里有两条信息：
- 「没找到算法」——**信息量为零**（不知道该干什么）
- 「花指令高度可疑，必须处理」——**明确的行动指令**

AI 选了后者。这是**理性的**，因为工具只给了它一个可执行方向。

### 3.2 第二步：试图修复不存在的问题

从 03:48 到 04:26，AI 反复在做同一件事：

```
03:48:23 [IDA] 越界地址 43/43 个不在映像内 —— 判定为「IDA 合成条目」
03:48:23 [IDA] py_eval 返回可执行段 ? 个 / 段内函数 ? 个，可用 0 个
03:48:24 [花指令探测] 跳转目标非对齐 39/7530（0.52%） ⚠ 高度可疑
```

同一个警告出现了 **6 次**（03:09、03:12、03:48、04:11、04:14、04:25）。这说明 AI 在同一个坑里反复尝试，每次重启分析都重新踩一遍。

而 `[IDA] 越界地址 44/159` 暴露了第二个问题：**IDA 把函数地址算错了**（`ImageBase=0x0`，对 PIE 文件是错的）。AI 拿到的"函数列表"本身就是废的。

### 3.3 第三步：预算烧在两件都不该做的事上

```
03:51:32 → 04:01:00  Tool-Use 深度求解  568 秒
04:22:35 → 04:26:48  Tool-Use 深度求解  253 秒
04:26:48 → 05:08:38  Tool-Use 深度求解  2510 秒   ← 最后以 aborted 结束
```

**合计约 56 分钟**（超过总时长的一半）花在"深度求解"上，而这三轮拿到的前提都是错的。

最后 2510 秒那轮直接 `aborted`——连结论都没输出。

## 四、更深一层：三个结构性缺陷

把这次失败拆开看，暴露的不只是一个阈值写错，而是**三个设计层面的问题**。

### 缺陷 1：「告警」被写成了「指令」

现在的文案是：

```
## ⚠ 花指令检测：本题高度可疑（必须处理）
```

问题在于**"必须处理"**这四个字。它把一条统计观察变成了行动命令，而 AI 没有能力判断这个观察是否可信（它看不到 0.52% 是什么概念）。

**这是工具对 AI 的误导**：AI 信任工具的判断，工具却给了一个不可靠的判断。

### 缺陷 2：零命中时不给「下一步做什么」

`scan_crypto` 报「未发现算法指纹」时，`note` 写的是：

> 这不等于"是壳"：可能是自实现算法、常量布局非常规…… 建议优先在本层找逐字节比较/位运算循环与内联常量表。

这段话说得**很诚实**，但它给的是"可能性清单"，不是"下一个动作"。

相比之下，「花指令高度可疑」给的是**明确的行动**。两相对比，AI 当然选后者。

**教训**：诊断型工具的输出，如果只给"可能是什么"，就等于把决策权丢回给 AI——而 AI 在信息不足时只能抓最像指令的那条。

### 缺陷 3：没有「前提校验」

`[IDA] 越界地址 44/159` 这个警告出现了 6 次，但从头到尾**没有任何机制阻止 AI 继续用这些函数列表**。

一台机器的函数表里 44 个地址越界，说明这个分析结果是坏的。但工具只是"警告"，然后继续把坏数据喂给 AI。

**教训**：数据完整性不达标时，应该**拒绝产出**而不是"带警告产出"。后者会让 AI 以为"虽然有点问题但应该能用"。

## 五、修法：不是调阈值，是改判据的方向

### 5.1 花指令告警：从「比例」改成「绝对量 + 比例」双条件

实测数据给出了清晰的分界：

```
题目:      0.518% ~ 1.152%
系统 DLL:  0.033% ~ 0.131%
分界点:    0.2% ~ 0.5% 之间
```

原条件 `bad >= 20 || ratio > 0.002` 里，`bad >= 20` 太松（notepad 23 个就中），`0.002` 太松（比系统 DLL 还低）。

应改为：

```js
// 双条件：绝对量足够多 + 占比明显高于正常程序基线
// 基线实测：8 个系统二进制 ratio 在 0.033%~0.131%，题目在 0.518%~1.152%
suspicious: bad >= 50 && ratio > 0.004
```

验证见下节。

### 5.2 更重要的是：加了 `elf_anomaly`

本轮新增的结构异常检测，让「零指纹」这个死胡同有了出口。同一份 elfstudy：

**旧输出（唯一的行动建议是花指令）**：
```
【(未发现算法指纹)】
[花指令探测] 0.52% ⚠ 高度可疑（必须处理）
```

**新输出（直接给出 8 个可验证的结构事实）**：
```
## ELF 结构级异常（确定性推导，与算法指纹正交）
- 架构 x86-64 / DYN(PIE) / entry 0x2e90；TEXTREL=true；RELASZ=63 条
- 高危信号：segment-slack-data、df-textrel、rela-count-mismatch、
            suspicious-relocations、reloc-addend-to-uncovered

## 段尾缝隙（segment slack）里的隐藏数据
- 文件偏移 0x1988 起 517 字节   ← 隐藏重定位表
- 文件偏移 0x7396 起 1741 字节  ← 加密的校验函数

## 可疑重定位
- #0~#3 RELATIVE r_offset=0x954/0x956/0x957/0x958 → .dynsym 内部
- #15 COPY r_offset=0x894 → .dynsym 内部

## 疑似"被掏空"的函数
- 0x3b30  endbr64 + 8×nop + ret
```

**AI 看到这个，不会去修花指令——因为工具告诉它「0x7396 有一块 1741 字节的隐藏数据」。**

配合 `blob_decrypt`，下一步直接解出校验函数：

```
★ #1 分数 103.97  xor-chain-word {"width":4,"direction":"down","key0":0}
   capstone: 194 条指令，覆盖 87.3%
```

从「零指纹 + 错误告警」到「两个精确偏移 + 可解密的密文块」，这才是工具该给的东西。

### 5.3 阈值修复的验证数据

| 条件 | 命中哪些文件 |
|---|---|
| `bad>=20 \|\| ratio>0.002`（旧） | elfstudy, license, fw_a, **ntdll, kernel32, user32, msvcrt, notepad** |
| `bad>=50 && ratio>0.004`（新） | **只有** license(1.152%), fw_a(0.746%), elfstudy(0.518%) |
| `bad>=200 && ratio>0.008` | 只有 license |

新阈值 **0 误报**，同时保留了对三道真题的检出。

注意 license 和 fw_a 本身**确实**有异常（license 是单步异常 VM，fw_a 是静态链接的大程序），
但它们的 ratio 高是因为包含大量数据段被误当代码扫——这也是个独立问题，
不过至少不再"对系统 DLL 也报"。

## 六、这次失败的通用教训

### 教训 1：工具的确定性判断，比它的"提示"更有杀伤力

`[花指令探测] ... ⚠ 高度可疑` 这个字符串，在 AI 眼里是**工具做完了量测后的结论**，而不是"一条统计"。

一旦工具用「确定」的语气说错话，AI 会把它当成事实基础，后面所有的推理都建立在这个沙地上。

**规则**：工具的置信度必须和它的**实测误报率**挂钩。没做过基线测量的判据，不许输出「高度可疑」这类强断言。

### 教训 2：「信息量为零」的结论会被「有行动指令」的结论挤掉

AI 面对两个选项时，会选**可执行的那个**，哪怕它是错的。

所以当工具只能给「没找到」时，必须同时给「那接下来查什么」。否则 AI 会自己抓一个"看起来能做的事"，而那个事往往是错的。

### 教训 3：重复出现的告警，说明上游有硬错误

`越界地址 44/159` 和 `跳转目标非对齐 0.52%` 各出现 6 次。每次 AI 重启分析都重新踩一遍。

如果工具能识别「同一个警告第 3 次出现」→ 说明上次的修复没生效 → 应该**换前提**而不是**重试**。

现在的工具已经有 `FailureLoopGuard`（按工具/错误类别/路径三键计数），但它拦的是"同一个工具调用"，拦不住"同一类错误警告"。

### 教训 4：数据坏了就别往下走

`44/159 个地址越界` 意味着函数表有 28% 是废的。这种数据应该**直接判为不可用**，让 AI 去修（比如重新打开 IDA、手动指定 ImageBase），而不是带着警告继续。

## 八、还应该做的（按优先级）

### P0：花指令阈值（一条代码改动，收益最大）

```js
// electron/main.js:3795
- suspicious: bad >= 20 || ratio > 0.002,
+ // 基线实测：系统二进制 0.033%~0.131%，题目 0.518%~1.152%
+ // 双条件避免"notepad 23 个就报警"和"比系统 DLL 还低的阈值"
+ suspicious: bad >= 50 && ratio > 0.004,
```

配套：`app.js` 里「必须处理」改成「可疑，先确认再动手」，并附上实测基线数字让 AI 自己判断。

### P1：数据完整性闸门

`越界地址 > 20%` 时，`ida_list_functions` / `ida_decompile` 应该**拒绝返回结果**并说明"函数表损坏，请先修 ImageBase 或重开 IDA"，而不是"带警告返回"。

### P2：同类告警升级

把"同一个 warning 文案第 N 次出现"纳入 `FailureLoopGuard`。第 2 次提示，第 3 次强制换前提。

### P3：零命中时强制给行动

`scan_crypto` 在「未发现指纹」分支，除了现在的可能性清单，必须附一句**具体的下一步工具调用**（现在是 elf_anomaly，以后可能更多）。

---

## 九、一句话总结

> 那次失败不是因为"题太难"，是因为**工具用一条必然误报的告警，把 AI 推向了错误方向**，
> 而 AI 在两个选项里只能选可执行的那个。
>
> 修法不是"让 AI 更聪明"，是**让工具少说错话、多说有用的**。
