## 二、两种模式的分工 `[已验证]`

### mode=boundary（默认，推荐）

**不改任何字节**，只输出"哪些地址是指令起点"。

原理：跳转目标**必须**是指令起点（否则程序跑不起来）→ "目标不在边界上"是**纠错依据**，
据此把目标强制当起点（IDA 的 MakeCode 语义），多轮迭代收敛。

### mode=linear / recursive（辅查）

快速定位"疑似花指令点"，输出 `flagset_short_skip` / `complementary_pair` 等候选 + nop 范围。
**不要直接拿它 patch 交差**——见第四节。

## 三、与 IDA 实测对照（决定性验证）`[已验证]`

2026-10-26，IDA 9.1 + ida-pro-mcp 实跑 matrix：

| 指标 | IDA 9.1 | 本工具 boundary-map |
|---|---|---|
| 识别出的指令数 | 15224 | **14649** |
| 未识别字节 | **45141 / 60674 = 74.4%** | **8325 = 13.7%** |
| 覆盖率 | 25.6% | **86.3%** |
| 函数数 | 54（其中 31 个是未命名的 sub_） | — |
| main(0x4e49) 反编译 | `int __cdecl sub_4E49(const char *format) { return printf(format); }` ← **完全错误** | — |

**结论：**

1. **IDA 在这道题上也被花指令彻底骗了**——它把 main 反编译成一句 printf，74.4% 的代码区
   没被识别成代码。不是"我们的工具没用"，而是"这题的花指令连 IDA 都过不去"。
2. 本工具的边界重建覆盖率（86.3%）是 IDA 的 **3.4 倍**（未识别字节少 5.4 倍）。
   说明"跳转目标强制对齐 + 多轮收敛"确实有效。
3. **能力边界**：本工具输出"边界图 + 不可达区间"，**不是可直接读的伪代码**。
   要得到伪代码，仍需 AI 拿着边界图解读，或与 IDA 交互修正。

## 四、走不通的路（实测数据，别重复）`[已验证]`

### ✗ 字节 patch 花指令 → 越修越乱

```
基线:        16878 指令 / 239 个非边界目标 / 不可解码 4
patch 53 处: 17188 指令 / 236 个非边界目标 / 不可解码 7
```

**根因**：`xor ecx,ecx; jnz +1; B8 <imm32>` 里 `jnz +1` 跳过的是 `mov` 的 opcode。
把 `xor+jnz` nop 掉后，那 1 字节独立、`mov` 缺前缀 → **制造新的错位**。
在"交叠污染"（264 处短跳转互相影响）场景下，逐个 nop 必然越修越乱。

**结论**：只有"花指令段前后都在正确边界上"时，整段 nop 才有效。
检测到 400+ 冲突时不要 patch，转 boundary 模式或动态。

### ✗ 把"跳转目标非边界"当花指令位置

那是**症状**（解码已偏），不是**病灶**。Matr1x 上会产生 239 个假候选。

### ✗ 把 `jmp $` / `call $+5; pop reg` 当花指令

前者是 PIC 取址（29 处，改成 call 后行为无变化）；后者也是 PIC 取址（39 处）。
工具已把它们统计为"排除项"。

### ✗ 只处理"互补跳转对"（jz/jnz 成对）

Matr1x 上 0 命中——它用的是 `xor r,r; jnz`（无配对 jz）。只覆盖一种形态 = 特解。

## 五、能力边界（诚实说明）

**能做到**：
- 检测花指令存在并量化（非边界跳转比例、冲突数、不可达字节）
- 定位**第一个解码偏移点**（`findFirstDivergence`：跳转来源、目标、目标处解码结果、前序指令）
- 重建比线性扫描/IDA 都自洽得多的指令边界图（86.3% vs 55.9% vs IDA 25.6%）
- 报告不可达区间（花指令垃圾块候选，附首字节供判断是否函数序言）

**做不到**：
- 静态把 400+ 冲突全部仲裁（交叠污染的根本判定需要执行证据）
- 直接产出可读伪代码
- 自动处理 call/ret 跳板（只报告，盲 nop 会破坏返回地址）

## 六、下一步（优先级）

1. **动态 grounding**（最可靠）：目标可运行时（Matr1x 在 Kali 上能跑），用 gdb 单步 tracing
   记录真实执行路径 → 真指令集合是地面真值 → 剩下的就是花指令。
2. **与 IDA 交互修正**：拿 boundary-map 的不可达区间/强制对齐点，在 IDA 里对照
   `MakeCode`/`undefine` 后的结果，形成"工具指路 → IDA 落实"的闭环。
3. 冲突仲裁增强：用"基本块内指令数一致性"或"哪条解码链能到达 ret"来裁决。


## 七、IDA 内修复（create_insn 路线）的实测边界 `[已验证]`

试过在 IDA 里直接改 IDB（更"正统"的路线，让 Hex-Rays 自己接手）：

```
py_eval: ida_bytes.del_items(head, DELIT_SIMPLE, span) + ida_ua.create_insn(addr)
结果: create_insn(0x27b0) = 5, size=5, bytes=b8fb60987a   ← 单次成功
      即 0x27b0 被正确解析为 mov eax, 0x7A9860FB
```

但**批量修复失败**，实测数据：

```
BEFORE code=15224/60674 (25.1%)
round 1: 201 个未对齐目标 -> 新建 1054 条指令
round 2-8: 201 个未对齐目标 -> 又新建 1054 条（完全重复）
AFTER  code=15224/60674 (25.1%)   ← 覆盖率一点没变
```

**根因**：IDA 的 auto-analysis 在每次 `auto_wait()` 时会用**它自己的控制流模型**
推翻手工建立的指令边界（不认可的指令被撤销/合并）。所以"手动 MakeCode + 让它重新分析"
在这个场景下会陷入"建了就被拆"的循环。

**关键 API 注意点**（踩坑记录）：
- `del_items` 和 `DELIT_SIMPLE` 都在 `ida_bytes`，**不在** `ida_ua`
- `create_insn` 无法在"已有指令内部"创建新指令（返回 False / "Failed to create instruction"），
  **必须先 del_items 破坏原边界**
- `py_exec_file` 的参数名是 `file_path`，且用**独立命名空间**执行 —— 里面 def 的函数
  `py_eval` 看不到；`py_eval` 内部用 `exec` 也有同样的命名空间隔离问题
  → 多步逻辑必须**完全内联**在单个 py_eval 字符串里
- MCP 的 `define_code` 参数是 `items: [{addr}]`，不是 `addr`

**要突破 auto-analysis 的反抗，只有两条路**：
1. **关闭 auto-analysis**（`ida_auto.enable_auto(false)`），手工修完边界后再开。
   代价：与 IDA 其他功能可能冲突，需改更多状态。
2. **动态优先**（推荐）：让程序真跑一遍，用 gdb / `ida_dbg` 记录**真实执行过的地址**，
   这些地址就是"IDA 必须接受的"边界——用**执行证据**覆盖它的启发式。

**结论**：静态 + IDA API 的路线在"交叠污染"题目上撞到了 IDA 自身 auto-analysis 的反抗。
这不是实现细节问题，而是"静态启发式 vs 静态启发式"的冲突 —— 必须引入第三种信息（执行证据）。

## 八、工具闭环：修复后必须重开 IDB（2026-10-26 补）`[已验证]`

### 问题

junk_repair 写出 `*_repaired` 后，AI 经常**接着在旧 IDB 上反编译**，读到的仍是按旧错位边界
解析的伪代码，于是误判"修补没用"，转而自己写脚本 nop 花指令 —— 那正是实测会让对齐继续恶化的做法。

根因不是模型不听话，而是**工具链缺一环**：IDA MCP 的 `open_file` 工具（ida-pro-mcp 的
discovery 组）此前**没有暴露成 AI 工具**，模型根本没有能力让 IDA 重新加载文件。
提示词里写"用 open_file 重开"，模型只能当它不存在。

### 修复

1. **新增 AI 工具 `ida_open_file({path, new_database?, timeout?})`**
   - 转发到 MCP 的 `open_file`，固定 `switch=true, autonomous=true`
   - `autonomous=true` 是必须的：否则新 IDA 起来弹模态框，MCP 端口注册不上，
     后续所有调用都超时（表现为"IDA 卡死"）
2. **junk_repair 写盘后自动重载并等待就绪**（`idaReloadAndWait`）
   - 先删除同名 `.i64`/`.idb`：`-A` 自治模式下"是否覆盖"对话框的默认回答不一定是"是"
   - 轮询 `server_health` 直到 `auto_analysis_ready && hexrays_ready`
   - 再轮询 `list_functions` 直到函数数连续两次相同（IDA 是增量识别，一次取样易拿半成品）
   - 失败时**不假装成功**：明确回报失败原因，并给出可手动执行的下一步
3. **提示词硬化**（`autoSolveBinaryFlag` 的 junkSection）
   - 三条硬禁令：禁止自写 nop 脚本 / 禁止在 junk_repair 前下算法结论 / 禁止用动态调试绕过
   - 五步强制顺序：junk_repair(dryRun) → junk_repair → ida_open_file → 重新反编译 → junk_scan
   - 并把该段的"不要调用任何工具"改成条件分支（命中花指令时**允许并鼓励**调工具）

### 回归锁定

`tests/test_tool_registration.js` 的 NEW_TOOLS 加入 `ida_open_file`，强制这个工具
**七处登记齐全**（schema / dispatch / KNOWN / MAP / toolLabel / precheck / 提示词），
少一处测试就红。当前 87/87 通过。

## 九、Matr1x 的算法结论（供后续复用，非通解）`[已验证部分]`

修补后二进制在 IDA 里得到 90 个函数、59 个可反编译。已确认的事实：

| 项 | 结论 | 证据 |
|---|---|---|
| 输入打包 | `packed[i] = ((c[2i]-0x30)<<4) \| (c[2i+1]-0x30)` | gdb 在 0x538D 读 `ebp-345`，与 32 字符输入逐字节验证 |
| 真实主体 | `sub_4EDF`（读入+打包）→ `sub_53A5` → `sub_4638`（校验）→ `sub_53D5`（比对+打印） | `sub_4E49`/`sub_4E67`/`sub_4EBE` 只是混淆切出的碎片 |
| `off_13200` | 6×9 = 54 个 dword（魔方 6 面×9 格） | `get_bytes 0x13020` |
| `off_13218` | 另一组 6×9 = 54 个 dword，与前者**零元素重合** | `get_bytes 0x130f8`；不是置换关系，是输出矩阵 |
| 打印分支 | `0x5B90` 打印 `ebp-0x180`；把 `0x5409` 的 `test eax,eax; jz` 强改为 `mov eax,1` 后，输出**与输入无关**（`6f ac 23 6b ...`） | 说明这是诱饵分支，flag 不在此处生成 |
| 校验比较常量 | 全程 3 条 cmp：`0x46b0`（循环上界 eax vs 6）、`0x4a8b`（eax 恒 -729248700）、`0x4e15`（eax 恒 -429430304） | 单步 trace 631 条指令，换输入后仍取同值 |
| 校验无循环 | `0x4638` 无论输入如何都是线性 631 步 | 全量单步 trace |
| 分派器 | `sub_39E3` 按字符选 12 个 handler；折叠后落 0x10-0x15 / 0x20-0x25 / 0x30-0x35 | z3 折叠 |

**未完成**：拿到"每行偶数位 5 个之和"与"奇数位 4 个之和"的 12 个预计算值。
它们既不在文件里为明文 dword，也不是 `off_13200` 任意 4/5 子集和
（已穷举 6 行 × 126 个 5 子集 + 126 个 4 子集验证）。官方算法描述指出需在"正确转动后"
取快照，因此这一步依赖先还原 `sub_39E3` 12 个 handler 对 54 格的置换语义 —— 这是后续工作。

**结论**：花指令修复链路已闭环并测得有效性；Matr1x 的算法还原卡在
"12 个转动 handler 的置换语义"，不是花指令问题。

## 十、端到端实测：修补到底带来了什么（2026-10-26）`[已验证]`

前面第九节说"Matr1x 算法还原卡住"，但**花指令链路本身是通的**。这一节是实测数据，
用工具链自己的产物跑出来的，不是旁路脚本。

### 10.1 工具链自测（junk_repair 内建输出）

现在 junk_repair 写盘后会自动复测并输出同口径对比表：

```
| 指标 | 修复前 | 修复后 |
| 跳转目标非对齐 | 301 | 70 |
| 可修补点 | 231 | 9 |
非对齐跳转下降 76.7%（字节长度不变: 是）
```

### 10.2 指令边界图对比（buildBoundaryMap）

| 指标 | 原始 | 修补后 | 变化 |
|---|---|---|---|
| 跳转目标非对齐 | 301 | 70 | -76.7% |
| 冲突点（交叠污染） | 427 | 32 | **-92.5%** |
| 强制对齐点 | 361 | 156 | -56.8% |
| 不可达区间段数 | 115 | 59 | -48.7% |
| 识别指令数 | 15244 | 15300 | +56 |

冲突点下降 92.5% 是这次修补有效性的**最强证据**：冲突点代表"同一地址被两种解码解释覆盖"，
正是花指令制造边界歧义的地方。它大幅下降说明修补真的解开了交叠污染。

### 10.3 IDA 侧效果（A/B 实测）

| 指标 | 原始 matrix | 工具修补版 | 变化 |
|---|---|---|---|
| IDA 识别函数数 | 54 | 90 | +36 |
| 可反编译函数数 | 35 | 50 | **+15** |
| 反编译成功率 | 87.5% | 65.8% | ↓（见下方警告） |

⚠️ **成功率下降是正常现象，不是变差**。原始 54 个函数里有 19 个是被花指令切碎的 `sub_*` 碎片，
成功率的分母小。修补后多出 36 个原本识别不出来的函数，其中 26 个是重度混淆的大函数，
拉低了百分比。**正确判据是"可反编译函数的绝对数"（35→50）**。

这条判读口径已写入：`junk_repair` 返回值、`autoSolveBinaryFlag` 提示词、skill ctf-obfuscation。

### 10.4 关键函数逐个对比（最硬的证据）

| 函数 | 作用 | 原始 | 修补后 |
|---|---|---|---|
| `0x53D5` | 比对并打印 flag | 反编译失败 | ✅ 197 字符伪代码 |
| `0x4EDF` | 读入 + nibble 打包 | 反编译失败 | ✅ 1242 字符伪代码 |
| `0x53A5` | 转调 | 反编译失败 | ✅ 232 字符伪代码 |
| `0x4638` | 核心校验 | 反编译失败 | 仍失败（最重混淆） |
| `0x39E3` | 字符分派器 | 反编译失败 | 仍失败 |

**这才是"修补真正可利用"的含义**：原来 5 个关键函数一个都读不出来，修补后 3 个可读。
剩下 2 个是混淆最重的函数，需要动态 tracing 配合（见第六节）。

### 10.5 多实例踩坑（本轮新发现）

机器上同时开多个 IDA 时，MCP 的 `open_file` 用"启动前后实例快照差集"判断哪个是新实例。
实测 4 个实例并存时它会静默返回 `port=undefined`（`message: "launched but did not register"`），
此时切换到根本没发生，后续量测全打在旧库上——**这会让 A/B 对比得出完全错误的结论**
（我第一次测就踩了：原始和修补版都显示 54 个函数、全部反编译失败）。

修复：`idaReloadAndWait` 在 `open_file` 无端口时走兜底——`list_instances` 按路径匹配，
再 `select_instance` 精确切换。实测切换后 `server_health.input_path` 正确指向目标文件，
且关键函数立刻可反编译（见 10.4）。回归测试已锁定这条兜底链路。
