## 二、两种模式的分工 `[已验证]`

### mode=boundary（默认，推荐）

**不改任何字节**，只输出"哪些地址是指令起点"。

原理：跳转目标**必须**是指令起点（否则程序跑不起来）→ "目标不在边界上"是**纠错依据**，
据此把目标强制当起点（IDA 的 MakeCode 语义），多轮迭代收敛。

### mode=linear / recursive（辅查）

快速定位"疑似花指令点"，输出 `flagset_short_skip` / `complementary_pair` 等候选 + nop 范围。
**不要直接拿它 patch 交差**——见第四节。

## 三、与 IDA 实测对照（决定性验证）`[已验证]`

2026-10-26，IDA 9.1 + ida-pro-mcp 实跑 matrix：

| 指标 | IDA 9.1 | 本工具 boundary-map |
|---|---|---|
| 识别出的指令数 | 15224 | **14649** |
| 未识别字节 | **45141 / 60674 = 74.4%** | **8325 = 13.7%** |
| 覆盖率 | 25.6% | **86.3%** |
| 函数数 | 54（其中 31 个是未命名的 sub_） | — |
| main(0x4e49) 反编译 | `int __cdecl sub_4E49(const char *format) { return printf(format); }` ← **完全错误** | — |

**结论：**

1. **IDA 在这道题上也被花指令彻底骗了**——它把 main 反编译成一句 printf，74.4% 的代码区
   没被识别成代码。不是"我们的工具没用"，而是"这题的花指令连 IDA 都过不去"。
2. 本工具的边界重建覆盖率（86.3%）是 IDA 的 **3.4 倍**（未识别字节少 5.4 倍）。
   说明"跳转目标强制对齐 + 多轮收敛"确实有效。
3. **能力边界**：本工具输出"边界图 + 不可达区间"，**不是可直接读的伪代码**。
   要得到伪代码，仍需 AI 拿着边界图解读，或与 IDA 交互修正。

## 四、走不通的路（实测数据，别重复）`[已验证]`

### ✗ 字节 patch 花指令 → 越修越乱

```
基线:        16878 指令 / 239 个非边界目标 / 不可解码 4
patch 53 处: 17188 指令 / 236 个非边界目标 / 不可解码 7
```

**根因**：`xor ecx,ecx; jnz +1; B8 <imm32>` 里 `jnz +1` 跳过的是 `mov` 的 opcode。
把 `xor+jnz` nop 掉后，那 1 字节独立、`mov` 缺前缀 → **制造新的错位**。
在"交叠污染"（264 处短跳转互相影响）场景下，逐个 nop 必然越修越乱。

**结论**：只有"花指令段前后都在正确边界上"时，整段 nop 才有效。
检测到 400+ 冲突时不要 patch，转 boundary 模式或动态。

### ✗ 把"跳转目标非边界"当花指令位置

那是**症状**（解码已偏），不是**病灶**。Matr1x 上会产生 239 个假候选。

### ✗ 把 `jmp $` / `call $+5; pop reg` 当花指令

前者是 PIC 取址（29 处，改成 call 后行为无变化）；后者也是 PIC 取址（39 处）。
工具已把它们统计为"排除项"。

### ✗ 只处理"互补跳转对"（jz/jnz 成对）

Matr1x 上 0 命中——它用的是 `xor r,r; jnz`（无配对 jz）。只覆盖一种形态 = 特解。

## 五、能力边界（诚实说明）

**能做到**：
- 检测花指令存在并量化（非边界跳转比例、冲突数、不可达字节）
- 定位**第一个解码偏移点**（`findFirstDivergence`：跳转来源、目标、目标处解码结果、前序指令）
- 重建比线性扫描/IDA 都自洽得多的指令边界图（86.3% vs 55.9% vs IDA 25.6%）
- 报告不可达区间（花指令垃圾块候选，附首字节供判断是否函数序言）

**做不到**：
- 静态把 400+ 冲突全部仲裁（交叠污染的根本判定需要执行证据）
- 直接产出可读伪代码
- 自动处理 call/ret 跳板（只报告，盲 nop 会破坏返回地址）

## 六、下一步（优先级）

1. **动态 grounding**（最可靠）：目标可运行时（Matr1x 在 Kali 上能跑），用 gdb 单步 tracing
   记录真实执行路径 → 真指令集合是地面真值 → 剩下的就是花指令。
2. **与 IDA 交互修正**：拿 boundary-map 的不可达区间/强制对齐点，在 IDA 里对照
   `MakeCode`/`undefine` 后的结果，形成"工具指路 → IDA 落实"的闭环。
3. 冲突仲裁增强：用"基本块内指令数一致性"或"哪条解码链能到达 ret"来裁决。


## 七、IDA 内修复（create_insn 路线）的实测边界 `[已验证]`

试过在 IDA 里直接改 IDB（更"正统"的路线，让 Hex-Rays 自己接手）：

```
py_eval: ida_bytes.del_items(head, DELIT_SIMPLE, span) + ida_ua.create_insn(addr)
结果: create_insn(0x27b0) = 5, size=5, bytes=b8fb60987a   ← 单次成功
      即 0x27b0 被正确解析为 mov eax, 0x7A9860FB
```

但**批量修复失败**，实测数据：

```
BEFORE code=15224/60674 (25.1%)
round 1: 201 个未对齐目标 -> 新建 1054 条指令
round 2-8: 201 个未对齐目标 -> 又新建 1054 条（完全重复）
AFTER  code=15224/60674 (25.1%)   ← 覆盖率一点没变
```

**根因**：IDA 的 auto-analysis 在每次 `auto_wait()` 时会用**它自己的控制流模型**
推翻手工建立的指令边界（不认可的指令被撤销/合并）。所以"手动 MakeCode + 让它重新分析"
在这个场景下会陷入"建了就被拆"的循环。

**关键 API 注意点**（踩坑记录）：
- `del_items` 和 `DELIT_SIMPLE` 都在 `ida_bytes`，**不在** `ida_ua`
- `create_insn` 无法在"已有指令内部"创建新指令（返回 False / "Failed to create instruction"），
  **必须先 del_items 破坏原边界**
- `py_exec_file` 的参数名是 `file_path`，且用**独立命名空间**执行 —— 里面 def 的函数
  `py_eval` 看不到；`py_eval` 内部用 `exec` 也有同样的命名空间隔离问题
  → 多步逻辑必须**完全内联**在单个 py_eval 字符串里
- MCP 的 `define_code` 参数是 `items: [{addr}]`，不是 `addr`

**要突破 auto-analysis 的反抗，只有两条路**：
1. **关闭 auto-analysis**（`ida_auto.enable_auto(false)`），手工修完边界后再开。
   代价：与 IDA 其他功能可能冲突，需改更多状态。
2. **动态优先**（推荐）：让程序真跑一遍，用 gdb / `ida_dbg` 记录**真实执行过的地址**，
   这些地址就是"IDA 必须接受的"边界——用**执行证据**覆盖它的启发式。

**结论**：静态 + IDA API 的路线在"交叠污染"题目上撞到了 IDA 自身 auto-analysis 的反抗。
这不是实现细节问题，而是"静态启发式 vs 静态启发式"的冲突 —— 必须引入第三种信息（执行证据）。

## 八、工具闭环：修复后必须重开 IDB（2026-10-26 补）`[已验证]`

### 问题

junk_repair 写出 `*_repaired` 后，AI 经常**接着在旧 IDB 上反编译**，读到的仍是按旧错位边界
解析的伪代码，于是误判"修补没用"，转而自己写脚本 nop 花指令 —— 那正是实测会让对齐继续恶化的做法。

根因不是模型不听话，而是**工具链缺一环**：IDA MCP 的 `open_file` 工具（ida-pro-mcp 的
discovery 组）此前**没有暴露成 AI 工具**，模型根本没有能力让 IDA 重新加载文件。
提示词里写"用 open_file 重开"，模型只能当它不存在。

### 修复

1. **新增 AI 工具 `ida_open_file({path, new_database?, timeout?})`**
   - 转发到 MCP 的 `open_file`，固定 `switch=true, autonomous=true`
   - `autonomous=true` 是必须的：否则新 IDA 起来弹模态框，MCP 端口注册不上，
     后续所有调用都超时（表现为"IDA 卡死"）
2. **junk_repair 写盘后自动重载并等待就绪**（`idaReloadAndWait`）
   - 先删除同名 `.i64`/`.idb`：`-A` 自治模式下"是否覆盖"对话框的默认回答不一定是"是"
   - 轮询 `server_health` 直到 `auto_analysis_ready && hexrays_ready`
   - 再轮询 `list_functions` 直到函数数连续两次相同（IDA 是增量识别，一次取样易拿半成品）
   - 失败时**不假装成功**：明确回报失败原因，并给出可手动执行的下一步
3. **提示词硬化**（`autoSolveBinaryFlag` 的 junkSection）
   - 三条硬禁令：禁止自写 nop 脚本 / 禁止在 junk_repair 前下算法结论 / 禁止用动态调试绕过
   - 五步强制顺序：junk_repair(dryRun) → junk_repair → ida_open_file → 重新反编译 → junk_scan
   - 并把该段的"不要调用任何工具"改成条件分支（命中花指令时**允许并鼓励**调工具）

### 回归锁定

`tests/test_tool_registration.js` 的 NEW_TOOLS 加入 `ida_open_file`，强制这个工具
**七处登记齐全**（schema / dispatch / KNOWN / MAP / toolLabel / precheck / 提示词），
少一处测试就红。当前 87/87 通过。

## 九、Matr1x 的算法结论（供后续复用，非通解）`[已验证部分]`

修补后二进制在 IDA 里得到 90 个函数、59 个可反编译。已确认的事实：

| 项 | 结论 | 证据 |
|---|---|---|
| 输入打包 | `packed[i] = ((c[2i]-0x30)<<4) \| (c[2i+1]-0x30)` | gdb 在 0x538D 读 `ebp-345`，与 32 字符输入逐字节验证 |
| 真实主体 | `sub_4EDF`（读入+打包）→ `sub_53A5` → `sub_4638`（校验）→ `sub_53D5`（比对+打印） | `sub_4E49`/`sub_4E67`/`sub_4EBE` 只是混淆切出的碎片 |
| `off_13200` | 6×9 = 54 个 dword（魔方 6 面×9 格） | `get_bytes 0x13020` |
| `off_13218` | 另一组 6×9 = 54 个 dword，与前者**零元素重合** | `get_bytes 0x130f8`；不是置换关系，是输出矩阵 |
| 打印分支 | `0x5B90` 打印 `ebp-0x180`；把 `0x5409` 的 `test eax,eax; jz` 强改为 `mov eax,1` 后，输出**与输入无关**（`6f ac 23 6b ...`） | 说明这是诱饵分支，flag 不在此处生成 |
| 校验比较常量 | 全程 3 条 cmp：`0x46b0`（循环上界 eax vs 6）、`0x4a8b`（eax 恒 -729248700）、`0x4e15`（eax 恒 -429430304） | 单步 trace 631 条指令，换输入后仍取同值 |
| 校验无循环 | `0x4638` 无论输入如何都是线性 631 步 | 全量单步 trace |
| 分派器 | `sub_39E3` 按字符选 12 个 handler；折叠后落 0x10-0x15 / 0x20-0x25 / 0x30-0x35 | z3 折叠 |

**未完成**：拿到"每行偶数位 5 个之和"与"奇数位 4 个之和"的 12 个预计算值。
它们既不在文件里为明文 dword，也不是 `off_13200` 任意 4/5 子集和
（已穷举 6 行 × 126 个 5 子集 + 126 个 4 子集验证）。官方算法描述指出需在"正确转动后"
取快照，因此这一步依赖先还原 `sub_39E3` 12 个 handler 对 54 格的置换语义 —— 这是后续工作。

**结论**：花指令修复链路已闭环并测得有效性；Matr1x 的算法还原卡在
"12 个转动 handler 的置换语义"，不是花指令问题。

## 十、端到端实测：修补到底带来了什么（2026-10-26）`[已验证]`

前面第九节说"Matr1x 算法还原卡住"，但**花指令链路本身是通的**。这一节是实测数据，
用工具链自己的产物跑出来的，不是旁路脚本。

### 10.1 工具链自测（junk_repair 内建输出）

现在 junk_repair 写盘后会自动复测并输出同口径对比表：

```
| 指标 | 修复前 | 修复后 |
| 跳转目标非对齐 | 301 | 70 |
| 可修补点 | 231 | 9 |
非对齐跳转下降 76.7%（字节长度不变: 是）
```

### 10.2 指令边界图对比（buildBoundaryMap）

| 指标 | 原始 | 修补后 | 变化 |
|---|---|---|---|
| 跳转目标非对齐 | 301 | 70 | -76.7% |
| 冲突点（交叠污染） | 427 | 32 | **-92.5%** |
| 强制对齐点 | 361 | 156 | -56.8% |
| 不可达区间段数 | 115 | 59 | -48.7% |
| 识别指令数 | 15244 | 15300 | +56 |

冲突点下降 92.5% 是这次修补有效性的**最强证据**：冲突点代表"同一地址被两种解码解释覆盖"，
正是花指令制造边界歧义的地方。它大幅下降说明修补真的解开了交叠污染。

### 10.3 IDA 侧效果（A/B 实测）

| 指标 | 原始 matrix | 工具修补版 | 变化 |
|---|---|---|---|
| IDA 识别函数数 | 54 | 90 | +36 |
| 可反编译函数数 | 35 | 50 | **+15** |
| 反编译成功率 | 87.5% | 65.8% | ↓（见下方警告） |

⚠️ **成功率下降是正常现象，不是变差**。原始 54 个函数里有 19 个是被花指令切碎的 `sub_*` 碎片，
成功率的分母小。修补后多出 36 个原本识别不出来的函数，其中 26 个是重度混淆的大函数，
拉低了百分比。**正确判据是"可反编译函数的绝对数"（35→50）**。

这条判读口径已写入：`junk_repair` 返回值、`autoSolveBinaryFlag` 提示词、skill ctf-obfuscation。

### 10.4 关键函数逐个对比（最硬的证据）

| 函数 | 作用 | 原始 | 修补后 |
|---|---|---|---|
| `0x53D5` | 比对并打印 flag | 反编译失败 | ✅ 197 字符伪代码 |
| `0x4EDF` | 读入 + nibble 打包 | 反编译失败 | ✅ 1242 字符伪代码 |
| `0x53A5` | 转调 | 反编译失败 | ✅ 232 字符伪代码 |
| `0x4638` | 核心校验 | 反编译失败 | 仍失败（最重混淆） |
| `0x39E3` | 字符分派器 | 反编译失败 | 仍失败 |

**这才是"修补真正可利用"的含义**：原来 5 个关键函数一个都读不出来，修补后 3 个可读。
剩下 2 个是混淆最重的函数，需要动态 tracing 配合（见第六节）。

### 10.5 多实例踩坑（本轮新发现）

机器上同时开多个 IDA 时，MCP 的 `open_file` 用"启动前后实例快照差集"判断哪个是新实例。
实测 4 个实例并存时它会静默返回 `port=undefined`（`message: "launched but did not register"`），
此时切换到根本没发生，后续量测全打在旧库上——**这会让 A/B 对比得出完全错误的结论**
（我第一次测就踩了：原始和修补版都显示 54 个函数、全部反编译失败）。

修复：`idaReloadAndWait` 在 `open_file` 无端口时走兜底——`list_instances` 按路径匹配，
再 `select_instance` 精确切换。实测切换后 `server_health.input_path` 正确指向目标文件，
且关键函数立刻可反编译（见 10.4）。回归测试已锁定这条兜底链路。

## 十一、运行期探测原语（v1.9.2）`[已验证]`

上一轮卡在"sub_39E3 的 12 个转动 handler 对 54 格的置换语义"——静态读混淆代码读不动。
这一轮补的不是"某个题的答案"，而是**让工具能自己量运行期行为**的四个原语。

### 11.1 四个原语

| 原语 | 解决什么 | 实现 |
|---|---|---|
| `ida_dbg(snapshot_diff)` | 反推"这段代码把数据改成了什么" | 跑一段 → 前后各拍内存快照 → **就地逐字节 diff**（快照存 IDA 侧，只回传变化项） |
| `ida_dbg(force_continue)` | 让被混淆提前打断的循环跑满 | 断点处 `idc.set_reg_value` 改寄存器 → continue/step，`repeat` 控制次数 |
| `ida_dbg(global_reads)` | 判断函数只校验一行还是一整块 | 遍历 `XrefsFrom` 统计数据引用 + 步长，元素数 < 一行宽度即单行校验 |
| `angr_solve` | 算法读不出但知道成功分支 | 生成 `call_state` 起跑 + 间接跳转 hook 的脚本 |

新增 `electron/dbg-probe.js`、`electron/angr-gen.js`；回归 `tests/test_dbg_probe.js`（82 条断言，
含"生成的 Python 必须能过 `ast.parse`"）。全量 **89/89**。

### 11.2 为什么写寄存器要用 `idc.set_reg_value`

实测：upstream MCP 插件（ida-pro-mcp）**没有写寄存器的工具**——`dbg_write` 只能写内存。
而 `ida_dbg` 模块里也没有 `set_reg_value`。正确的 API 是 IDAPython 的 `idc.set_reg_value(value, name)`
（注意参数顺序是 value 在前）。第一版生成代码误用了 `ida_dbg.set_reg_value`，被回归测试抓出。

### 11.3 angr 路线的两个硬前提

上一轮失败的两处，现在都固化进生成器：

1. **`entry_state` 必死**：先进 `__libc_start_main`，该调用不返回，simulation manager
   直接耗尽（实测 0 个 state）。必须 `factory.call_state(主函数)`。
2. **间接跳转必须 hook**：混淆函数经全局函数指针跳转，angr 会顺指针把常量表字节当代码解码，
   报 `IR decoding error at 0x413231`（那地址在 `.rodata` 里）。把跳转点写进 `hooks` 后只按真实目标走。

生成器默认 `auto_load_libs=False`（CTF 目标多为裁剪过的静态链接，解析 libc 常直接失败），
并在解出后做一次 `VERIFY_FOUND` 复核；失败时打印 `ERR0=<地址>`，便于发现**下一个**未 hook 的点。

## 十二、Matr1x 逆向：用 Unicorn 把结构彻底挖开（2026-10-27）`[已验证]`

第十一节说"还差最后一步"，这一轮用 **Unicorn 模拟执行**把结构全部落地了。
关键工具组合：`unicorn`（执行）+ `capstone`（反汇编）+ `pyelftools`（段解析），本机 Python 3.12 全有。

### 12.1 为什么 Unicorn 能突破静态分析

前几轮卡住的原因：`sub_4638` 有 628 条指令、Hex-Rays 反编译失败、常量被混淆成算术恒等式。
但它是**纯计算函数**，不需要操作系统支撑 —— 只要能映射段、给对参数，Unicorn 就能跑。

两个必须踩对的坑：

1. **base 必须是 0**，不是 0x400000。代码里是绝对地址（`mov eax, [0x13298]`），
   按 0x400000 加载会让所有全局读取落到未映射区。
2. **VA → 文件偏移要按 PT_LOAD 换算**。数据段 `vaddr=0x12ed4` 但 `p_offset=0x11ed4`，
   直接拿 VA 索引文件会读到错误数据（我第一版就是这么错的）。

### 12.2 已确证的结构（全部来自运行期实测，非猜测）

### 12.4 花指令定位（这轮最有价值的副产品）

```asm

39d3    push eax
39d4    call $+5          ; e8 00 00 00 00
39d9    pop  eax          ; eax = 0x39d9
39da    add  eax, 0xa      ; eax = 0x39E3   <- 真实目标
39dd    push eax
39de    jmp  0x39df       ; e9 fc ff ff ff -> 落到 0x39E0 !
```

`0x39DE` 的 `jmp` 目标是 `0x39E0`，而 `0x39E0` 是 `add eax,0xa` 的**中间字节**，
解码出来是非法指令 —— 这就是典型的花指令：**跳到指令中间**。
Unicorn 在这里直接报 `UC_ERR_INSN_INVALID`，反而**帮我定位到了花指令**。

**这正是 junk_repair 的 F01 类（假跳转 / 非对齐跳转）**。此前的工具在 matrix 上报了 231 处 F01，
这一处就是其中之一；手工 hook 掉它（把 `0x39DE` 重定向到 `0x39E3`）后，`sub_39E3` 才被执行。

### 12.5 当前卡点（诚实记录）

Unicorn 跑完整路径时，`sub_39E3` 只被调用 **1 次**（应为 32 次，每个输入字符一次），
`sub_4638` 只比较 1 轮就退出（`var_4` 首次不符归零）。
原因：`sub_4EDF` 是 `__usercall`，输入参数走寄存器我的传参约定还没对。

下一步最直接的两条：

1. **hook `scanf`（0x4E67）**，直接返回 32 并把字节写进它期望的缓冲区，
   这样就不用猜 `eax` 是长度还是指针。
2. 或从 `0x53A5` 起跑（`0x4EDF` 调 `sub_4638` 的真正中转），参数在栈上更好定位。

结构已经全部挖开（指针布局、目标表、循环次数、12 种置换），剩下的是**把输入喂对**这一步。

### 12.6 追加实测：CALC.lo 铁证，CALC.hi 是污染值

Unicorn 拿到的 12 个比较值，其中 LO 的 6 个**全部精确等于 M1 行偶列和**：

```
row1 M1even=0x2eec7c99 CALC.lo=0x2eec7c99  EQ
row2 M1even=0xd62cd6a4 CALC.lo=0xd62cd6a4  EQ
row3 M1even=0x460e73a8 CALC.lo=0x460e73a8  EQ
row4 M1even=0xac589fc6 CALC.lo=0xac589fc6  EQ
row5 M1even=0x7ddb8603 CALC.lo=0x7ddb8603  EQ
```

而 HI 的 6 个值（0x67941bc3 等）**不匹配任何 M1/M2 的组合**。
原因：`0x4e15` 在 `0x4a8b` 之后执行，中间的 `0x4a98 and ecx,eax` / `0x4ac2 mov [ebp+var_4],ecx`
已把 `var_4` 归零（首次比较必然不等），后续 `edx` 被复用为别的中间量 —— **是污染值，不代表真实语义**。

所以正确做法是：**先让 LO 比较通过**（即找到让 row 偶列和 == T.lo 的矩阵状态），
再看 HI 的真实含义。当前卡在"如何到达那个矩阵状态"。

### 12.7 深度搜索的负面结果（重要）

用 12 种置换做 DFS（深度 8）搜索，**score 恒为 0**：没有任何转动序列能让任意一行的
`(偶列和, 奇列和)` 同时等于任一 `T[i]`。单次转动后也没有任何行匹配。

这说明：**T 不是对 M1 直接转动后的行和**。可能的方向：

1. `T` 与 `M2`（加密矩阵）有关，而非 M1 的变换结果；
2. 转动的输入不是"M1 的 54 个元素"，而是别的东西（例如某个初始化解）；
3. `T` 需要与另一组值（如输入派生的密钥）共同满足。

**结论：结构已挖到底，但"T 的语义"仍未确定。** 这不是工具能力问题，是这道题
在最后一层语义上还需要更多轮次推演。

## 十三、Obfuscating Macros II：用 Unicorn 完整解码 VM（2026-10-30）`[已验证]`

这道题比 Matr1x 更纯粹地展示了"工具能力缺口"：AI 在 496 秒里做了 67 次 run_python、
21 次 IDA 反编译，把结构猜了个七七八八，但**始终没跑起来**，最后卡在
"1024 次循环左移等于恒等"这个错误结论上。真实原因有两个：

1. 它把 `sub_4045F2` 当成了 pop，实际那是 **push**（内部调 `sub_404BF2`）；
2. 它不知道 C++ 容器可以打桩，于是被 `operator new` 挡在门外。

### 13.1 程序结构（静态即可确认）

```
main (0x403DC4):
  cin >> s           ; 读字符串
  if (len(s) != 16) -> Failed
  v11 = *(u64*)s       ; 前 8 字节
  v12 = *(u64*)(s+8)   ; 后 8 字节
  (v13, v14) = sub_401006(v11, v12)
  cout << v13 << " " << v14
  if (v13 == 0xA1E8895EB916B732 && v14 == 0x50A2DCC51ED6C4A2) -> "Congratulations!"
```

注意：**程序会先把变换结果打印出来再判断**，所以它同时是个 oracle。

### 13.2 VM 结构（Unicorn 实测）

`sub_401006` 是一台**栈式 VM**，有三套容器：

| 容器 | 用途 | 关键 API |
|---|---|---|
| `[rbp-0x80]` | 标签字典 map，91 个条目 | `0x40456A(map, &idx)` 取 slot 地址 |
| `[rbp-0xD0]` | 标签栈 | `0x40459A` 弹出 |
| `[rbp-0x120]` | 数据栈（`std::vector<u64>`）| push `0x404BF2` / pop `0x404CC0`（经 `0x404634`）|

标签号是**混淆过的**：`demux(x) = (x ^ 0x78ABDA5F) - 0x57419F8E`（函数 `0x4040A2`）。
注册模式固定为 `mov [slot], 0xXXXXXX` —— 所以只要让同一 label 拿到同一 slot，
整个 map 就可以用 Python dict 替代。

### 13.3 跑通 VM 的三个关键打桩

```python
# 1) map：同一 label 必须拿到同一 slot 地址
def hook_map(uc, ...):
    real = demux(rdq(uc, rsi))
    if real not in LABELS: LABELS[real] = new_slot()
    ret_to(uc, rsp, LABELS[real])

# 2) TLS：fs:[0x28] 栈保护 canary，否则第一步就 UC_ERR
uc.reg_write(UC_X86_REG_FS_BASE, TLS)
uc.mem_write(TLS + 0x28, struct.pack("<Q", 0x1122334455667788))

# 3) operator new：bump allocator，否则 0x407113 跳进 PLT 后 RIP=0
if nm == "_Znwm":
    p = heap_ptr[0]; heap_ptr[0] = (p + sz + 15) & ~15
    ret_to(uc, rsp, p)
```

**其余栈操作一律不 hook** —— 给足堆内存后 `std::vector` 自己就能跑对。
（我第一次 hook 了 push/pop，结果得到"恒等变换"的假结论，因为把 push 当成了 pop。）

### 13.4 真实算法（1024 轮 × 8 条指令）

跑通后统计执行频次，核心算术只有 8 条、各 1024 次：

```
1024x  0x402487  not  rax              ; v8 = ~v7
1024x  0x402337  xor  rax, rdx         ; v8 = v8 ^ v6
1024x  0x4025FA  movabs rax, 0x8000000000000000   ; MSB 掩码
1024x  0x402604  and  rax, rdx         ; v8 = v7 & MSB
1024x  0x4026FA  add  rax, rax         ; v7 <<= 1
1024x  0x402715  and  rax, rdx         ; v8 = v6 & MSB
1024x  0x402A2E  add  rax, rax         ; v6 <<= 1
1024x  0x402113  add  rax, rdx         ; v8 = v8 + X
```

也就是每轮：**128 位整体左移 1 位，最高位回填到最低位（循环移位）**，
再按条件做 `+` / `^` / `~`。1024 轮 = 8 × 128，纯循环移位部分恰好是恒等，
真正提供混合的是 `+`（带进位）那一条。

### 13.5 实测性质（测的是"能否代数求逆"，不是"能否反解"）

用 Unicorn 当 oracle 做黑盒测量：

| 检验 | 结果 |
|---|---|
| GF(2) 仿射性（f(a^b) ?= f(a)^f(b)^f(0)） | **否** |
| 可加性（f(a,b) ?= f(a,0)+f(0,b)-f(0,0)） | **否** |
| 单比特翻转的平均影响位数 | **31.6 / 64**（完全雪崩） |
| 对合性 f(f(x)) ?= x | 否 |

这四个检验否定的只是"用一条代数公式一步求逆"。它们**不能**否定整体可逆——
我在 13.6 就犯了这个推理错误。见下。

### 13.6 结论修正：我判断错了，循环体是可逆的 `[已验证]`

上一轮我写"雪崩 31.6/64、非仿射、非可加 ⇒ 无法反解"。**这个结论是错的。**

题目作者给出的最终伪代码如下（把 92 段合并之后）：

```
def func(X, Y):
    for _ in range(0x400):
        if X & 1 == 0:  Y ^= ~X
        else:           Y ^=  X
        X = ~X

        XX = X & 0x8000000000000000
        YY = Y & 0x8000000000000000
        X <<= 1
        Y <<= 1
        if YY: X |= 1
        if XX: Y |= 1

        tmp = Y
        Y = (Y + X) & MASK
        X = tmp

        XX = X & 0x8000000000000000
        YY = Y & 0x8000000000000000
        X <<= 1
        Y <<= 1
        if YY: X |= 1
        if XX: Y |= 1
    return X, Y
```

**每一条都是可逆的**：

| 操作 | 逆操作 |
|---|---|
| `Y ^= ~X` / `Y ^= X` | 再异或一次同一个值（XOR 自逆） |
| `X = ~X` | 再取反（自逆） |
| `X <<= 1; if YY: X \|= 1` | `X = (X >> 1) \| (XX_bit << 63)`，其中 `XX_bit = X & 1` |
| `tmp = Y; Y = Y + X; X = tmp` | `t = X; X = Y; Y = (Y - t)` —— **注意顺序** |

所以从 `(0xA1E8895EB916B732, 0x50A2DCC51ED6C4A2)` 出发，把 1024 轮**逆序**跑一遍，
就能得到 `(X0, Y0)`，拼成 16 字节即输入。几毫秒的事。

**为什么我的"雪崩/非仿射"测量没否定可逆性**：
可逆 ≠ 线性。`+`（带进位）会让它雪崩、破坏仿射性，
但只要每一步都是**双射**，整体就仍然是双射，就能逐轮倒推。
我当时的四个检验（仿射性/可加性/对合性/雪崩）测的都是"能不能用代数公式一步求逆"，
而逐轮倒推不需要任何代数公式——**这才是正确的第一反应**。

这是本轮最重要的一条通用教训，已写进 `skills/ctf-obfuscation/SKILL.md` §5.4 与工具提示词：
> 算法读出来后，先问"这个循环能不能倒着走"，能就别上 Z3/angr。

### 13.7 通用的解题链路（这次的真正产出，不是特解）

题目作者的原话是：*"One possible solution is to record a execution trace and set those jump target."*
这句话把人类的手工流程说得很清楚，而工具此前**完全缺这两个能力**。现已补上：

| 环节 | 工具 | 产出 |
|---|---|---|
| ① 记录执行轨迹 | `emu_trace` | 每个间接跳转点 `src → 实际 dst` 及当时操作数值；全部控制流边；执行过的区间 |
| ② 回填给 IDA | `ida_apply_trace` | 对目标 `create_insn`、对边 `add_cref`、可选 `add_func` |
| ③ 正向模型对拍 | `emu_trace` 的 `regs.rax/rdx` | 用真值校验读出的伪代码 |
| ④ 逆序反解 | 纯 Python | 逐轮倒推得到输入 |

`emu_trace` 在结构同型的测试 ELF（92 段、`jmp rax` 分发）上实测：

```
STOP=finished
INSNS=832  EXEC_RANGES=92  EDGES=182  IND_SITES=1
RAX=0x9dfc266ecbc6d314 RDX=0x665544332210eecb
IND 0x40180e -> 90 targets: v=0x402080 0x402080(x1) v=0x4020c0 0x4020c0(x1) ...
```

一个 `jmp rax` 点自动量出 90 个目标、且段地址等距 0x40；
正向模型与仿真返回值**逐位一致**（见 `tests/fixtures/verify_model.py`）。

### 13.8 三个必须知道的打桩要点（都是踩出来的）

1. **TLS canary**：`fs:[0x28]` 不设 `UC_X86_REG_FS_BASE` 会第一步就 `UC_ERR_READ_UNMAPPED`。
2. **`operator new`**：C++ 题必挂。GOT 槽与 `.plt` 桩都要重定向到同一组 mini-libc，
   否则 `RIP=0`。这一步不做，任何 `std::map`/`std::vector` 题都跑不起来。
3. **不要 hook `std::vector` 的 push/pop 去简化语义**。
   我第一次就是这么做，结果把 push 当成了 pop，得出"恒等变换"的假结论。
   **给足堆内存，让真实代码自己跑**——这是唯一不会自欺的做法。
