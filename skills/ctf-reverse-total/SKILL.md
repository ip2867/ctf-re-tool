# CTF 逆向全流程总纲

> 本文是 `ctf-dispatch` / `ctf-reverse-binary` / `ctf-reverse-tooling` / `ctf-antidebug` /
> `ctf-crypto-identify` / `ctf-iot-firmware` 等专项技能的总纲与决策索引。
> 只想知道"下一步做什么"看本文；需要某类题的完整操作细节再 `read_skill` 对应专项。

## 零、三条贯穿全部题型的原则

1. **"没看到"不等于"没有"**。静态工具报"无算法指纹"/"一堆空函数"，往往是代码被藏在
   段外、被加密、或被逐条解密执行。此时该做的是**找结构上的不自洽**，不是换算法硬猜。
2. **把"能不能解"变成"数据够不够"**。结构摆清楚 + 确定性指标判定，比灵光一现可靠。
   - 页尾缝隙 → 有偏移就能取；加密 blob → 有密文就有明文（只要算法在候选集里）
   - Feistel → 有公式就能换元降维；OTA → 有描述符就能拼、有摘要就能对账
3. **自洽不等于正确**。模型/脚本内部回代通过，只能说明推导自相一致；
   **必须与原程序、官方题解或已知前缀对拍**。常数取错时正向回代依然能过（用的是同一套错常数）。

## 一、接手一道题：先判型，再定路线

| 输入特征 | 类型 | 走哪条路 |
|---|---|---|
| `.exe/.dll` native / `.so/.elf/.out` | PE/ELF | 本文 §三 起 |
| `.exe` 含 mscoree | .NET | dnSpy + de4dot |
| `.apk/.dex/.jar` | Android | `ctf-reverse-android`（JEB MCP 优先） |
| `.pyc/.pyo` / PyInstaller / PyArmor | Python 字节码 | `ctf-reverse-langs` §1 |
| 有 `gopclntab`/`main.main` | Go | `ctf-reverse-langs` §2（GoReSym 恢复符号） |
| 有 `core::panicking`/mangled 符号 | Rust | `ctf-reverse-langs` §3（rustfilt） |
| `.luac` / LuaJIT | Lua | `ctf-reverse-langs` §4（注意版本字节） |
| `.wasm` | WASM | wasm2wat / wasm-decompile |
| 固件 / 无扩展名 bin / OTA 包 / 路由 dump | IoT | 本文 §九 |
| `.js/.mjs` 混淆 / 加密参数 sign/token | Web JS | `ctf-jsreverse` |
| 输入是方向串（wasd/udlr），程序在网格上走 | 迷宫 | 本文 §六 迷宫 |
| 逻辑读懂但手算不完 | 自动化求解 | 本文 §六 |

**成本阶梯（每步都要产出证据，别跳步）**：
`strings(1s)` → `scan_crypto`(秒) → 反编译(1min) → **静态锁定函数+写调试假设(1~2min)** →
定向动态调试(5min) → 爆破/符号执行（不确定）

## 二、开工顺序：三条硬性先后

这三条来自真实题目，顺序错了会白烧大量时间。

1. **先结构检测，再反编译**。校验逻辑可能根本不在任何函数里。
   直接反编译会看到一堆 `endbr64; nop×8; ret` 空函数，然后误判"这题没逻辑"。
2. **先解出密文，再识别算法**。在密文上跑常量扫描当然"无命中"——那是**正确结果**。
   解出明文后再扫，常量和结构才会浮现。
3. **先化简搜索空间，再上算力**。三轮 Feistel 直接枚举是 2^64（不可能）→
   换元降到 2^32；并且**用 C 不用 Python**（实测 18 秒 vs 40 分钟）。

## 三、结构级异常：静态工具"看不见"的第一类

正常编译器产出的元数据是自洽的。一旦有人做加载期自修改，必然留下痕迹。
用 `elf_anomaly` 一次查完 8 类矛盾：

| 检出项 | 判据 | 意味着什么 |
|---|---|---|
| `segment-slack-data` | LOAD 的 `p_filesz` 未页对齐，页尾有非零数据 | **内核按整页映射**，这些字节运行期可读（可执行段还可执行） |
| `df-textrel` | 动态表含 `DF_TEXTREL` | 运行期会写代码段 → 有人在改 `.text` |
| `rela-count-mismatch` | `RELASZ` ≠ `.rela.dyn` + `.rela.plt` 条数 | ld.so 重定位遍历**终点被挪动过** |
| `suspicious-relocations` | COPY/RELATIVE 的 `r_offset` 落在 `.dynsym` 内 | 用加载器**改写符号表项**（伪造 `st_value`） |
| `ifunc-symbols` | `STT_GNU_IFUNC` + `st_shndx=SHN_ABS` | ld.so 会在**加载期直接调用** `st_value` 处 |
| `reloc-addend-to-uncovered` | addend 指向不被任何 section 覆盖的数据 | 引用了一块藏在缝隙里的数据 |
| `hollow-functions` | `endbr64 + nop×N + ret` | 被掏空的函数，等着被改成跳板 |
| `uncovered-file-region` | 文件里有不被任何 section 覆盖的数据块 | 隐藏数据 |

**四条实现级陷阱**（自己写这类检测时会踩）：
1. 页尾**不能按整段平均判**——真实样本常是「大片零 + 中间夹真数据」，整段非零比只有
   13%，会漏判。必须滑窗（窗口 128 / 步长 32）找连续块再合并。
2. **NOBITS（`.bss`）不算文件覆盖**——它在文件里不占字节。算进去会让覆盖率超 100%，
   把真数据误判成"已被节覆盖"。
3. **节表本体要算已覆盖**——`e_shoff..e_shoff+e_shnum*entsize` 是合法结构数据，
   但不属于任何 section。
4. **只有 RELATIVE(8)/COPY(5) 的 addend 才有文件偏移语义**——PC32/GOTPCREL 的 addend
   是指令内位移常量（常见 0x10/0x18），按文件偏移解释会大面积误报。

**交叉验证手段**：在 IDA 里问 `py_eval` 某个地址属于哪个段。
若 IDA 回答 `seg=NONE loaded=False`，就印证了"这段确实不在任何 section 里"——
这比 readelf 更有说服力，因为用的是 IDA 自己的加载器。

## 四、加密 blob：静态"看不见"的第二类

**关键认知**：这类解密是**纯数据变换**，与程序其余部分无关 → **不需要跑程序**，
不需要 ptrace、不需要 Unicorn，离线就能复现。

`blob_decrypt(offset, length, kind)` 的做法：
1. 穷举候选家族（chain-XOR 按 1/2/4/8 字节宽、滚动 XOR/ADD、单字节、LCG 流）
2. 逐个试解
3. 用**可判读性**打分排序：
   - `kind=code` → **capstone 指令覆盖率**（最强信号，解对了几乎全覆盖）
   - `kind=text` → 可打印比例
   - 通用 → 熵下降 + 零字节比例

实测：某题 816 字节，正确答案得分 **103.97**，第二名只有 12.73。解出明文以
`90 90 90 90 f3 0f 1e fa 53 55 41 54 48 89 e5`（nop×4 + endbr64 + push rbx/rbp/r12）
开头——一眼就是函数序言。

**链式 XOR 的确切定义**（别记反）：
```
key = 0
for i = N-1 downto 1:            # 从高地址往低地址
    P[i] = C[i] ^ key
    key = (key + P[i]) & mask    # 累加的是明文
P[0] = C[0]                      # 索引 0 不变
```
⚠️ **它不是自逆的**：拿解密函数当加密函数用会得到错误结果。

## 五、算法识别与变体还原

### 5.1 常量指纹速查

| 常量 / 特征 | 算法 | 还原要点 |
|---|---|---|
| `0x9E3779B9` | TEA/XTEA/XXTEA | 看轮数与移位：`<<4 >>5`=TEA；key 数组轮换=XTEA；按块遍历奇偶配对=XXTEA |
| S 盒 `63 7C 77 7B F2 6B 6F C5` | AES | 找 KeyExpansion 确认 key 长度；ECB/CBC 看 IV |
| S 盒 `D6 90 E9 FE CC E1 3D B7` | SM4 | 32 轮非平衡 Feistel + 线性变换 L |
| FK `a3b1bac6 56aa3350 677d9197 b27022dc` | SM4（**铁证**） | 系统参数出现即为 SM4 |
| IV 以 `0x7380166f` 开头 + 64 轮 | SM3 | **哈希不是加密**：等值比较→爆破；逐字节比较→截断逆推 |
| `0x67452301 0xEFCDAB89 …` | MD5 | 不可逆，只能碰撞/爆破 |
| SHA1 IV 同上前两 dword | SHA1 | **只能靠字节序区分**（MD5 小端 / SHA1 大端） |
| `0x6A09E667 0xBB67AE85` | SHA256 | 同上 |
| `0xEDB88320` | CRC32 | 注意自定义初值/异或值 |
| 256 字节 S 盒初始化 + i/j 双索引 | RC4 | KSA+PRGA；变体常改 drop-N |
| 8 字节块 + 16 轮 Feistel | DES | key 8 字节 |
| `"expand 32-byte k"` | ChaCha20/Salsa20 | 流密码 sigma（字符串形态） |
| `0x243F6A88 0x85A308D3` + 4×256 项 S 盒 | Blowfish | 18 项 P 数组 |
| 4-bit S 盒 + 位置换层 | PRESENT / 轻量分组 | 64 位块、31 轮 |
| 逐字节 XOR + 固定 key | XOR | key 长度 = 密文周期；用 `flag{` 首部可直推 |

**⚠️ 字节序陷阱**：SM3 IV 在部分二进制里以 **LE word** 存放（`6f168073…`），
只搜 BE 会误判"没有 SM3"。两种字节序都要试。

**⚠️ 假阳性**：大二进制（>16MB）里的标准库常量是噪声（BoringSSL 的 sigma 等）。
工具会把这类降为 `low` 置信度——看到 `low` 不要当成"这题就是这个算法"。

**⚠️ 假 ELF 头**：`.eh_frame` 里可能含 `7f 45 4c 46`（`0x7f` 是 DWARF 操作码）。
校验内嵌 ELF 时必须同时检查 `e_type ∈ {1,2,3,4}` 且 `e_machine ∈ [1,260]`。

### 5.2 拿到 S 盒后的决策树

```
scan 发现 256 项双射 S 盒
├─ 与标准表完全相同        → 标准算法，直接用标准库
├─ 逐项 XOR / ADD 常量     → 表被平移，还原标准表或照抄题目表（等价）
├─ GF(2) 仿射（可逆矩阵）  → 表被线性混淆，用工具给的 A/c 还原
└─ 无可还原关系（全新表）  → 直接从文件读表，按骨架结构实现：
     · 32 项 dword 与标准 SM4 CK 有固定差分 → SM4 骨架
     · Rcon 形态（01 02 04…）              → AES 骨架
     · 8 字节块                            → DES/Blowfish 方向
     · 都不是                              → 完全自定义，反编译确认轮循环
```

**魔改点清单**（变体题 90% 只改这些）：SM4 常改 S 盒/FK/CK（整体 XOR/加常量），
不改轮数(32)与线性层 `rol(2,10,18,24)`；AES 常改 S 盒与 Rcon，不改 MixColumns 结构。
验证方法：看被改表与标准表的**差分是否固定**。

## 六、逻辑读懂但手算不完：求解器选型

| 题目特征 | 用什么 | 为什么 |
|---|---|---|
| 逐字节/逐位**独立**校验（`out[i]=f_i(in[i])`） | **逐位枚举** | 每位置只需试 95 个可打印字符，比 Z3 快 |
| 校验逻辑复杂但方程明确（异或链/循环移位） | **Z3** | 约束直接编码 |
| 输入经过大量分支，静态读不动 | **angr** | 给 find/avoid 地址，免翻译 |
| 自写 VM / 自定义字节码 | **Unicorn** | 只模拟执行，不改写逻辑 |
| 校验 = 可逆轮函数 + 线性混合（Feistel/ARX + GF(2) 矩阵） | **`arx_solve`** | 手推矩阵必错，工具做确定性代数 |
| 迷宫/状态机（走法即输入） | **BFS/DFS + 模拟器** | 别手走 |

**调用式偷懒**：若二进制里有**可独立调用**的加密函数（无全局状态、无外部依赖），
不要复刻算法——用 Unicorn 当黑盒反复调用，逐字节枚举候选。判据：同输入两次输出一致。

### 6.1 Z3 十个高频坑

1. **`^` 只对 `BitVec` 成立**——`Int('x') ^ Int('y')` 直接抛异常。位运算一律 `BitVec`。
2. **右移要用 `LShR`**（逻辑），`>>` 是算术右移会带符号位。
3. **查表必须用无符号比较 `ULT`**——`If(v < k, ...)` 按**有符号**比较，
   索引 ≥ 0x80 被当负数，**前 128 项全查错**，外部表现是"有解却报 unsat"，极难定位。
4. **`ZeroExt` 参数顺序**——z3 原生是 `ZeroExt(位宽, 值)`（位宽在前），
   按直觉写 `ZeroExt(b, 24)` 会抛 `Z3Exception`。
5. **位宽选错是最常见的"解不出来"**——按反编译的变量声明定宽度。
6. **逐字节累加要逐步 `& 0xff`**——`sum(b)+i` 与 C 的 `uint8_t` 逐步累加语义不同。
7. **乘数与被模数不互素会凭空无解**——`v * 0x1234 ≡ C (mod 2^32)` 当乘数为偶数时必然无解，
   先验算 `gcd(乘数, 2^32)`。
8. **不要把约束拼成大字符串再 exec**——长约束（S 盒展开可达 8 万字符）会撞 Windows 命令行
   32K 上限。
9. **`unsat` 是有效结果不是工具坏了**——说明约束组自相矛盾，回头查推导
   （算术右移、字节序、漏前置约束）。
10. **解出后必须回代验证**——模型可能绕过你没写进去的隐式约束（宽度溢出、可打印域、前缀）。
    把模型字节喂回原校验函数跑一遍，相等才算解出。
11. **多解要显式排除再枚举**——`sat` 只保证给一个解，加
    `Or([x != m[x] for x in flag])` 再 check 才知道是否唯一。
12. **z3 副本陷阱**（VM 题踩过 10 小时）——对 flag 做 encode 时必须
    `encoded = encode(flag.copy())`，否则符号变量与位运算优先级混乱，
    解出的值满足约束但不是真 flag。

### 6.2 三轮 Feistel 换元（把 2^64 降到 2^32）

结构：`F_i(x) = x ^ g_i(x)`，`g_i(x) = Q_i · S(P_i · (x ^ k_i))`
（S 逐字节 S-box，P/Q 是 4×4 GF(2) 可逆矩阵）

```
设 t = U ^ V ^ W，则：
    g1(U) = t ^ yL
    g2(V) = t
    g3(W) = t ^ yR
⇒ U = g1⁻¹(t^yL),  V = g2⁻¹(t),  W = g3⁻¹(t^yR)
⇒ 判据：U ^ V ^ W ^ t == 0，只需枚举 32 位 t
命中后：L = W ^ yL,  R = U
```

**必须先验证这三条恒等式**：拿一组已知 (L,R) 正向算出 U/V/W 代入检查。
不成立说明 `g` 定义错了——`g⁻¹(z) = P⁻¹·(S⁻¹(Q⁻¹·z)) ^ k`，**k 在最外层**。

**实现选择**：C + `-O3 -march=native` = **18 秒**；Python+numpy ≈ 40 分钟；JS ≈ 30 分钟。

**多候选是正常的**：实测同一组参数命中 8 个候选。三轮 Feistel 输出不唯一，
**必须**每个候选都喂回原程序验证，不要看到第一个就交。

## 七、VM / 字节码题：四种形态

| 形态 | 识别特征 | 解法 |
|---|---|---|
| **标准 dispatch** | `while(1){ switch(dst[pc]) }`，case 8~15 个 | 按 case 复刻模拟器 |
| **单指令 NAND-only** | 没有 switch，只有一条 `v[a]=~(v[b]&v[c])` 反复执行 | 输入常是独立 XOR 链 → z3 建模 |
| **大数组电路型** | 几万项平坦数组 + 变长指令 + 恒定控制流 | 先 `vm_disasm` 切基本块 |
| **异常驱动（SMC）** | 逐条解密→执行→再加密，配 SIGTRAP/SIGSEGV handler | 进程内取证，不要单步 |

**必拿数据（缺一不可，代码与数据同等重要）**：
1. 解释器的**完整反编译**（所有 case 分支）
2. 常量数据表的**原始数据**：地址 + 按元素宽度小端解码
3. 反编译 refs 里被引用的全局（`src_`、密文表、格式串）要回头全部读出来

只有解释器没有字节码表时**不可解**，不要臆测。

**求解套路（写模拟器，勿纯脑推）**：按反编译逐 case 复刻小型模拟器，
输出缓冲通常与输入同下标独立变换 → 每位置**可独立暴力**。
拿已知输入先验证模拟器行为（能打印出 banner 即说明管道通了），再反解。

**已知陷阱**：
- 校验常量按**有符号 int8** 存放：`-89` 即 `0xA7`，比较两边都要 `& 0xff`
- "就地写回" opcode 会覆盖输入缓冲，改变后续读到的值——模拟器不能偷懒跳步骤
- 大数组型：**mem 必须可扩容**（程序数组只是内存的一部分，结果会写到程序区之外）
- **恒定控制流 ≠ 无解**：失败串是常量输出，说明"选择"发生在数据单元上而非跳转上

**循环分割识别法**：伪指令上千行时，找一个"边界指令"（固定寄存器被赋值、`jmp to fun0`），
以它为界切块，每块结构几乎一致（只是下标+1）→ 只分析第一块，其余照推。

## 八、定向动态调试：纪律与取证

### 8.1 入场条件（四条全满足才启动调试器）

**动态调试不是探索手段，是取证手段。** 它只回答"这个值运行时是多少"，
不回答"这段代码在干什么"——后者静态反编译更便宜。

1. **有函数清单**（`list_funcs`）
2. **每个候选有职责描述**（一句话说清：读输入/做变换/比对/解壳）
3. **写得出调试假设**：断点地址 + 命中后读哪个表达式 + 期望值 + 怎么判定
4. **有办法把执行流逼到那里**（入口断点/输入触发/改 IP）

**写不出第 3 条 = 静态还没读够，回反编译，不要启动调试器。**

### 8.2 环境自检：SSH 通 ≠ 能动态调试

| 症状 | 真因 | 判定与处理 |
|---|---|---|
| 断点不命中 / attach EPERM | `yama ptrace_scope=1` | 读 `/proc/sys/kernel/yama/ptrace_scope`，改 0 |
| 完全没有断点能力 | 远端没装 gdb / gdbserver | `command -v gdb`、`command -v gdbserver` |
| 自检报 `No such process` | 自检程序自己写错 | TRACEME 后必须先 `raise(SIGSTOP)` 等父进程再 CONT |

**判据是"实测"不是"看配置"**：`ptrace_scope=0` 也可能因容器 seccomp 失败，
所以顺序必须是「ptrace 实跑结果优先，scope 值只作参考」。

### 8.3 断点选址优先级

| 优先级 | 位置 | 理由 |
|---|---|---|
| 高 | 变换函数入口/出口 | 各断一次即得"输入原值→输出值"整段映射 |
| 高 | memcmp/strcmp 调用点 | 直接看到"期望 vs 实际" |
| 中 | 解密循环内部 | 只在需要轮密钥/中间态时 |
| 避免 | 消息循环、sleep、CRT 初始化 | 等于没断 |

**一次命中批量读**：寄存器 + 3 处关键内存 + 调用栈，不要来回单步几十次。

### 8.4 三个高频假故障

- 断点"设了却不命中" → 目标在断点生效前就跑过去了（给 sleep 窗口，或先在入口断）
- PIE 目标用静态地址下断点失效 → 必须用运行时重定位后的地址
- 运行态单步/写内存失败 → 先 `suspend` 或等断点命中

### 8.5 断点位置差一条指令就读错

典型：`jal 0x10818` 之后才有变换结果，断在 `jal` **之前**读到的还是原值。
判据：如果读出来的值等于输入/等于静态文件里的常量，说明断早了。

## 九、反调试与确定性取证

### 9.1 综合绕过优先级（按成本，别跳步）

1. **换执行环境**——Unicorn/Qiling 模拟天然无调试器痕迹。检测点只在"识别调试器"时有效，
   **模拟执行根本不触发**。这是最省力的一步，却最常被忘。
2. **通用插件/脚本先行**——Linux 用 gdb 反反调试脚本；Windows 用 ScyllaHide；
   Android 用 Frida 脚本。先把标准检测点盖住，再看残留。
3. **定位检测点**——从崩溃/退出点回溯，条件断点 + 日志。别猜。
4. **patch 语义**——改检测函数的返回值或跳转，而不是 nop 掉整段。
5. **最后才硬啃自定义检测**。

**判定"真的被挡了吗"**：先不挂调试器跑一遍。如果正常跑也失败，那不是反调试问题，
是输入/环境问题——别把时间浪费在绕过上。

### 9.2 信号类反调试（Linux 最常见，且与程序逻辑融为一体）

| 手法 | 表现 | 处理 |
|---|---|---|
| `SIGILL` 切换执行模式 | 撞非法指令后 handler 改上下文继续 | **别 patch 掉**，让信号真正抛给进程 |
| `SIGFPE` handler 里 mprotect 改代码 | 除零后代码段被改写 | 同上，信号是流程的一部分 |
| `fork` + pipe 死分支 | 父进程等子进程写管道，调试器只跟一个 | `set follow-fork-mode child` |
| `INT3`/`0xCC` 扫描 + 代码段 hash | 下断点即退出 | 先 patch 校验函数，再用硬件断点 |
| `rdtsc`/时间差 | 单步导致时间异常 | Hook 时间函数返回固定值 |
| 单步检测（`pushfq` 查 TF） | 一旦单步就走错分支 | **不要单步**，改用内存轮询 |

### 9.3 单步异常驱动 VM：确定性取证路线

这类题的"反调试"和"程序主逻辑"纠缠在一起，硬绕会走错分支。可靠做法是
**先钉死环境，再让程序自己跑，只在关键点观测**：

1. **确定性优先**：`personality(ADDR_NO_RANDOMIZE)` 关 ASLR。
   否则同一输入每次跑栈地址不同，hash 链跟着变，任何 diff 都无意义。
2. **干掉噪声源**：反调试函数首字节改 `0xC3`（ret）；`/proc/self/status` 的
   `TracerPid` 会进 VM 的 hash —— 把它 open 的路径重定向到假文件让值恒为 0，
   而不是去对抗 ptrace。
3. **别用 ptrace 观测 TF 单步的 VM**：VM 自己要收 SIGTRAP，ptrace 会先截走，VM 直接崩。
   改用 `/proc/<pid>/mem` 轮询（不需要 attach）。
4. **`/proc/<pid>/mem` 差分轮询**：以 16 字节块为单位反复 `pread` 目标区域，
   只记录变化的块 → 得到"程序写了哪里、写了什么"的完整序列，完全不干扰运行。
   代价是轮询间隔（约 4ms）内的多次写会合并。
5. **进程内 dump（无竞态）**：在目标进程里注入 shellcode（放进**已废弃函数的死代码区**，
   注意不要覆盖任何真实函数），在拒绝/失败瞬间把 VM 区整块写文件。
6. **区分"控制流"和"数据流"**：若两个不同输入的执行轨迹完全一致而结果不同，
   说明分支由**数据**决定 —— 别再追 RIP，去比对内存内容。

## 十、多架构固件与 OTA

### 10.1 先定界，再进大镜像

| 文件 | 大小 | 身份 |
|---|---|---|
| `fw_a` | ~1MB | 校验/打包器，**x86-64** |
| `fw_b.bin` | ~3KB | 目标固件，**RISC-V 32 位** |
| `ota_package.bin` | ~200B | 升级包，flag 常在这里 |

**架构不一致是常态**：x86 工具负责校验 ARM/MIPS/RISC-V 的镜像。不要因为"跑不起来"
就以为文件坏了。`ldd` 报"不是动态可执行文件"是静态链接的**正常表现**。

### 10.2 先跑校验器看 usage

```bash
./fw_a
# usage: ./fw_a <ota_package.bin> <keymat_hex32> <vm_out8_hex16>
```

这一步给出参数个数与类型，比反汇编找 argv 使用点快十倍。

### 10.3 OTA 结构（三个坑）

```
QWBP | ver(u32) | key16 | count(u32) | entry[] | 段数据
                                     └─ entry = { off(u32) len(u32) hash(u32) }
```

- **描述符步长未必 8 字节**——实测是 `(off, len, crc)` 三元组 = **12 字节**
- **片段不连续**——直接对原始字节哈希必然错，必须先按描述符拼
- **CRC 可能校验明文**——实测 OTA 存密文，但描述符 CRC 等于**明文**的 CRC32。
  这个观察直接证明"密文 + 明文校验和"结构

尾部标记块（`<标记><u32 LE 长度><数据>`）是 flag/密钥最常待的地方。
长度字段是**小端**——按大端读会得到远超文件大小的值，可用这点快速判字节序。

### 10.4 缺参数怎么办

`vm_out8_hex16` 这类参数通常来自**另一个固件的运行输出**：
1. 该固件能跑 → `qemu-riscv32 ./fw_b.bin`，抓它的 write 输出
2. 跑不起来 → 先看它是不是**只是打印一段常量**。3KB 固件的输出几乎一定在
   `.rodata`，直接读就有，不必真跑

**Unicorn 仿真 RISC-V 的两个坑**：
- `mem_map(0x100000, ...)` 可能失败（该版本有对齐限制）→ 改从 `0x0` 映射
- `UC_RISCV_INSN_ECALL` 在部分版本不存在 → 改用 `UC_HOOK_CODE` 判断指令字
  `0x00000073`，命中后读 `a7`（syscall 号）/`a0·a1·a2`

### 10.5 用校验器当 oracle

校验器有"通过/不通过"两个出口。构造候选参数喂进去看退出码：
```bash
./fw_a ota.bin "$KEY" "$VMOUT"; echo rc=$?
```
这比盲试快，也比赛猜算法可靠。

### 10.6 跨架构动态取值（本工具环境）

| 场景 | 工具 |
|---|---|
| RISC-V 32 位固件 | `qemu-riscv32 -g <port>` + `gdb-multiarch` |
| 无 qemu 对应架构 | Unicorn（注意 `UC_ARCH_RISCV` 需 capstone 5.0+） |
| 宿主机 objdump 无对应后端 | 一律用 `gdb-multiarch` 反汇编 |

## 十一、编码层与 PRNG

### 11.1 编码链剥层

多层编码（Base64 → ROT → XOR → 栅栏…）不要每种组合写一个脚本试。
`recipe` 一次执行整条变换链，给出每层的 printable 比例、熵、hex、预览。

- **判据**：某层之后 **printable 比例跳到 >90%** 且熵明显下降 → 真明文在这一层之下
- 顺序不确定时按"解码方向"排（编码是反向叠加的）
- **别当万能**：遇到自定义表/魔改算法仍要手写

### 11.2 PRNG 不是加密

逆向里的"加密"常是 PRNG（LCG / MT19937 / xorshift）。

- **LCG 参数恢复**：差分消元求模数。**原始值消元的 gcd 恒为 1，无用**；
  `pow(-1)` 能否成功取决于 `c` 的奇偶而非"模 2^k"。
- **已知明文推算子**：若有已知明文对，直接解出状态，不必预测 `rand()`。

## 十二、内嵌载荷（多阶段题第一步）

数据段里可能有"编码存储的下一层载体"。`scan_crypto` 的载荷流水线会直接定位并给提取脚本。

| 形态 | 判据 |
|---|---|
| 单字节 XOR/ADD × stride 1/2/4 | `buf[i]^buf[i+s]==0x17` / `(buf[i+s]-buf[i])&0xff==0x0d`（MZ 的编码差与密钥无关） |
| 周期 XOR（2/3/4/8） | 周期 2 直接由 MZ 解出；更大用 DOS stub 已知明文 |
| 滚动 XOR/ADD | `out[i]=in[i]^in[i-1]`；预筛 `out[0]==0x4d` |
| Base64/Hex 文本 | `TVqQ` / `4d5a` |

**关键护栏**：`key=0` 表示明文，**不能**算"内嵌载荷"——否则每个正常 PE/ELF 都会
把自己报成"内嵌自己"。偏移 0 + key 0 必须跳过。

**第一层是 loader 时本层零指纹是对的**，必须先把下一层提取出来再分析。

## 十三、验证闭环（不可省）

**AI 说解出来了不算解出来。** 每条结论都要过这四关：

1. **正向回代**：解出的输入喂回原校验函数，看是否通过
2. **与原程序对拍**：能跑原程序就跑，看它是否输出成功/flag
3. **阴性对照**：改一位输入，确认被拒（证明是真校验，不是条件写漏）
4. **与外部基准对拍**：官方题解、已知前缀、文件摘要

**自洽 ≠ 正确**（重复强调）：模型内部回代只能证明推导自相一致。
常数取错时正向回代依然通过，因为用的是同一套错常数——必须走第 2、4 关。

**多候选时**：全部喂回原程序，不要看到第一个就交。

## 十四、踩坑速查（按症状）

| 症状 | 先查什么 |
|---|---|
| 反编译出一堆空函数 | 是不是页尾缝隙藏代码 → `elf_anomaly` |
| `scan_crypto` 零指纹 | 密文/壳/loader → 先解 blob 或提取下一层，**这是正确结果** |
| 算出的 flag 正向回代通过但原程序拒绝 | 常数从静态读错了（那段是加密的），必须读运行时 |
| 断点命中但读到的值等于输入 | 断早了，往后挪一条指令 |
| 动态阶段整段落空 / Hook 0 命中 | 先查环境：frida client 与 server 版本是否一致 |
| 装了 APK 反复失败 | 双 adb 互杀 / package 服务未就绪 |
| 输入对但说 wrong | 有隐含变换，Hook 比较函数看"期望值"到底是什么 |
| 找不到比较点 | 搜成功/失败串的交叉引用；或对输入内存下写断点 |
| 算法认出但解不出 | 字节序/编码搞错 → 列假设组合用 `[HYPOTHESES]` 枚举 |
| 有壳静态看不了 | `upx -d` / dump；VMP 类直接动态 Hook 加密 API |
| 工具报"命令不存在"但 SSH 是通的 | 区分"命令写错"与"连不上"，看错误前缀 |
| 函数名查不到 | mingw 入口是 `_main`；C++ mangled 名按子串匹配 |
| 函数列表全是 CRT 噪声 | `__decode_pointer`/`_add_key_dtor` 名字里恰好含 decode/key，要降权 |
| 花指令扫描对正常文件大面积报警 | 阈值问题，正常二进制也有少量 `0x0f 0x0b` 类字节 |
| IDA 加载某地址报 `seg=NONE` | 该地址不在任何 section（页尾缝隙），这是**线索不是故障** |

## 十五、输出契约

- Flag：`[FLAG]flag{...}[/FLAG]`
- 验证数据：`[VERIFY]{"algo":"...","key":"hex","ciphertext":"hex|base64","encoding":"hex","expected":"..."}[/VERIFY]`
  custom 算法附 `code`（完整可跑的 Python 解密函数）
- 多候选：`[HYPOTHESES][{...},{...}][/HYPOTHESES]`
- 经验沉淀：`[EXPERIENCE]题型特征→关键套路/踩过的坑→下次怎么做[/EXPERIENCE]`（最多 5 条）
  - 写"学到了什么"，不写流水账；失败题的经验往往比成功题更值钱
