# 用真实解题日志迭代工具

> 这份流程来自多次实战：每次用户跑完一道题把日志贴过来，就按这套走一遍。
> 目标**不是**把那道题解出来，而是让工具下次能自己解出来。

## 0. 一条铁律：只补通解，不补特解

**绝对不要**把某道题的常量、函数地址、题名写进工具或知识库。
判断标准很简单——**这条改动换一道同类题还成立吗？**

| 特解（禁止） | 通解（要的） |
|---|---|
| "若地址是某个具体值就……" | "若发现 `jmp rax` + 运行期算目标，就走 trace 回填" |
| "某个常量值说明是某条曲线" | "看到特定形状的掩码 + 循环体是 `^ ~ + 移位`，先判可逆性" |
| "某题被切成 N 段要这样合" | "大量互不相连的短片段 + 间接跳转 = 分段 dispatch" |

自检：把改动写完后，搜一遍有没有具体题名/地址/常量混进 skill 或提示词。
（`tests/test_reversibility_discipline.js` 就是这么自动检查的。）

## 1. 审日志：把"失败"分类，不要笼统说"没解出来"

逐条扫工具调用与返回，按**失败原因**归类，每类给出证据行号：

| 类型 | 长得像什么 | 对应修法 |
|---|---|---|
| **A. 工具根本没有这个能力** | AI 反复用 `run_python` 手写同样的脚本（例：自己搭 Unicorn） | 新增工具/原语 |
| **B. 工具能算但接口别扭** | 一次任务要 5~7 次调用才能凑出效果；参数要手算偏移 | 合并成一个复合原语 |
| **C. 工具报错方式误导** | 返回 "无输出" 被当成成功；超时只说 "failed" | 改错误契约 + 加下一步提示 |
| **D. 平台/环境差异** | Windows 上 `| head` 失败、路径分隔符、编码乱码 | 适配层（别让模型记平台差异） |
| **E. 模型不知道有这个工具** | 明明有 `ida_open_file`，却手工去敲 IDA | 补进提示词/skill 的"何时用" |
| **F. 模型知道但用错顺序** | 先 `junk_patch` 后才发现要 `junk_repair` | 在工具描述里写死顺序 |

> 实测经验：**A 类最少但价值最高**，D 类最多但最容易修。
> 先修 A/D，再看 E/F——因为工具不好用时，模型再怎么"会用"也没用。

## 2. 区分责任：是工具的缺口，还是知识的缺口

同一份日志里这两种混在一起，必须分开记：

- **能力缺口**（工具做不了）→ 写代码，加工具
- **知识缺口**（工具能做，但不知道该做）→ 写 skill / 提示词

例：一道题的日志显示卡在"某个 handler 对一块数据做了什么"——
  当时 `snapshot_diff` 这类原语还不存在 ⇒ **能力缺口**；
  补上之后 AI 仍不去调用 ⇒ **知识缺口**（提示词没写"读不懂就别硬读，直接量"）。

## 3. 补能力：优先做"复合原语"，而不是"更细的原子操作"

模型不缺 `mem_read`。缺的是**一次调用完成一个认知闭环**：

| 想要的认知 | 不是 | 而是 |
|---|---|---|
| 这段代码改了什么 | 读前后内存各一次，自己 diff | `snapshot_diff`（跑一段+前后快照+就地差分） |
| 这个循环该跑几次 | 断点+单步+N 次 continue | `force_continue`（改寄存器+继续+repeat） |
| 这段代码运行期跳去哪 | 手工搭模拟器 | `emu_trace`（跑+记录+汇总跳转表） |
| 跳转目标怎么回到 IDA | 手工写 IDAPython | `ida_apply_trace`（create_insn+add_cref+add_func） |

**设计要点**（每条都踩过）：
1. **返回"结论"而不是"原料"**。差分会直接给 `off/before/after`，不要让模型自己比 hex。
2. **失败要给下一步**。超时不能说 "timeout"，要说"缩小搜索空间 / 拆成多次短脚本"。
3. **必须在摘要里给出可对拍的真值**（如 `regs.rax/rdx`），否则模型无法验证自己的模型。
4. **体积上限 + 截断上报**。`py_eval` 走 MCP，塞几万条边会直接超时。
5. **通用化**：桩要覆盖 `_Znwm/memset/memcpy/strlen/puts` 这些**常见**导入，
   而不是某道题用到的那个。

## 4. 补知识：写"何时用 + 判据 + 决策表"，不写"操作步骤"

skill 里最没用的是一长串命令；最有用的是一句**判据**：

- ❌ "调用 emu_trace，然后调用 ida_apply_trace，然后 decompile"
- ✅ "看到大量互不相连的短片段 + `jmp rax` + `mov [rbp-X], <数字>`，就是分段 dispatch，
   先 trace 再回填"（条件 → 动作）

判据要**可辨认**（在 IDA 里长什么样）、**可否定**（什么时候不该用）。
再配一张"操作 → 逆运算"之类的速查表，比流程描述好用得多。

## 5. 用测试锁住，否则下次就退化

每个修复都要有测试，且测试要**真的能失败**：

1. **结构断言**：生成物里必须包含关键 API（`create_insn`、`add_cref`）。
2. **语法校验**：生成的 Python 必须能被 `ast.parse` 通过（不是靠肉眼看）。
3. **端到端**：现场构造一个同型样本，真跑一遍，断言输出正确
   （例：`tests/fixtures/make_dispatch_fixture.py` 生成 92 段的 ELF，
   `test_emu_trace_e2e.js` 断言量出 90 个目标且段地址等距）。
4. **反面断言**：确认"不该做的"没做（不含具体题名/地址；正常代码不被误判）。
5. **对拍**：独立实现的模型与工具真值必须逐位一致。

> 没有第 3 条的测试基本是假保护——它只能证明"代码没语法错"。

## 6. 交付：双仓 + 回归 + 如实报告

```
① 源码仓 ctf-tool-v2        git commit
② 镜像仓 ctf-re-tool-publish 逐个文件复制（它是独立目录，不是 submodule）
                             在镜像仓再跑一次测试，确认镜像可用
                             git push（需先 git config http.proxy）
③ 全量回归 node tests/run_all.js —— 必须 100% 通过才提交
④ 版本号三处一致：package.json / src/index.html 的 version-badge / 启动.bat
```

报告时**只说验证过的**：
- 哪条修复有实测数据（给出具体数字）
- 哪条只是改了提示词（没跑过真实题目就明说）
- 哪些结论是上一轮错了、这一轮修正了（**主动认错比含糊过去有价值**）

## 7. 每轮结束前的自检清单

1. [ ] 所有改动都是通解？搜过题名/地址/常量了？
2. [ ] 每个修复都有能真失败的测试？
3. [ ] 端到端样本跑通，且数字对得上？
4. [ ] 全量回归 100%？
5. [ ] skill / 提示词写的是"判据"而不是"步骤"？
6. [ ] 双仓都已提交，镜像仓测试通过？
7. [ ] 报告里区分了"已验证"与"仅改文档"？
8. [ ] 有没有上一轮的结论需要修正？（有就明确写出来）

## 附：最常见的八类缺口与对应做法（实战沉淀）

| 缺口 | 典型日志特征 | 做法 |
|---|---|---|
| 只为"读"设计，不能"跑" | AI 手写 Unicorn/gdb 脚本 | 加执行类原语（trace/diff/force） |
| 结果要人肉比对 | 返回大段 hex，AI 自己 diff 到超时 | 工具侧就地算差值，只回变化项 |
| 混淆下静态结论不可信 | 反编译读得通但与真值不符 | 一律以运行期地面真值为准 |
| 平台差异泄漏给模型 | Windows 上 `\| head`、编码乱码 | 适配层兜住，别写进提示词 |
| 错误被当成成功 | "无输出"=成功；超时=空结果 | 失败前缀 + 下一步建议 |
| 知识写成特解 | skill 里出现具体题名/地址 | 改成"特征 → 动作"的判据 |
| **分诊把一整个类型漏掉** | 某类文件总走"通用兜底"分支，日志里出现完全不相干的分析步骤（如源码题在跑固件熵块采集） | 补类型分支 + 补能力判据；**别只补扩展名表，要看已有能力字段是否被消费** |
| **失败原因归错类** | 报"契约无命中/复现失败"，但题目本来就没有可解的东西 | 区分"解错了"与"这题离线不可解"，后者不能报成工具失败 |

### 两个特别容易漏的判据

**① 算出来但没用上的能力字段。**
典型：`decideRoute` 里 `capabilities.textual` 早就计算好了，路由却只用
`archive/fs/pcap/executable` 判断，于是纯文本落到 `local-probe`（= 走通用探测）。
**审日志时看到"某类文件总走最通用的那条分支"，就去检查分诊函数里有没有
已算出却没被 if 用到的字段。**

**② "失败"其实是"前提不成立"。**
验证闭环报"契约无命中"分两种情况，处理方式完全相反：
- 有密文但解错了 → 回灌证据让 AI 修正（这是正常循环）
- **根本没有密文** → 题目设计上 flag 不在本地，硬凑契约只会让 AI 编答案
  → 应明确报"本地无密文，需外部条件"，并禁止 AI 编造 `[VERIFY]`

判据：`contracts.every(c => !c.ciphertext)` → 属于后者。

### 另外两类：环境幻觉 与 转录错误

**③ 环境工具"静默失败"，报错信息却指向别处。**
实测（NaughtyBoy）：`NoxConsole.exe launch -name:Nox_1` 报 `player is not exist!`
—— 听起来像"模拟器实例没装"，实际是 `NoxConsole` 本身有 bug；**直接双击 `Nox.exe` 就能起**。
类似地，`frida` 报 `connection closed` 听起来像"服务没起来"，实际是**客户端与服务端版本不一致**
（服务端进程在、端口也通，只是握手即断）。

> 判据：**同一条命令，换一种调用方式/换成显式路径再试一次**。
> 若换法就通了，那不是环境坏，是工具链某层有 bug —— 这一层应该写进代码做回落，
> 而不是留给下次再踩。

**④ 从反汇编里"抄"出来的常量，抄错一位极难反查。**
实测：`cmp byte ptr [rbx+5], 74h  ; 't'` 被抄成 `bytecf{`（丢了一个 t），
于是所有输入在第一步就被拒，而日志只报"校验失败"——看起来像算法错，实际是转录错。

> 判据：**凡是逐字节 `cmp ..., imm` 形成的字符串（前缀/密钥/magic），一律让工具从立即数还原**，
> 不要靠读伪代码。伪代码会把它们折叠成人眼可读的字符串，而人会记错。
> 这类错误的现象是"卡在最开头、且看不出为什么"，与"算法读不懂"的体感完全不同 ——
> 出现"第一步就失败"时，**先去核对常量，不要往深处挖**。

### 判据汇总：什么时候该"改工具"而不是"再试一次"

| 现象 | 该做什么 |
|---|---|
| 同样的操作换种方式就成功 | 把回落写进代码（①） |
| 报错信息与真实原因不符 | 改错误契约，补上真实原因与修复命令（③） |
| 卡在最开头、且无法解释 | 先核对常量/前缀（④），再谈算法 |
| 用户/模型反复手工做同一件事 | 做成工具（见 §3） |
| 约束"无交集" | 先怀疑自己的某个前提，别扩大搜索空间 |
