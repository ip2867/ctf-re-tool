# PE 加载器 / 内嵌 PE / VM 解释器型逆向（含"魔改标准算法"识别）

> 实战来源：xmctf **Disguise**（花指令 + 文件隐藏 + VM 三层）。第一层给假 flag，真逻辑在内嵌 stage2 的 VM 里，VM 实现的是**魔改 SM4**。本页提炼"三层伪装题"的通用拆法。

## 一、三层结构速览

```
Disguise.exe（第一层）
├── 假校验：读输入 → 每字节 -= i → 与表 0x480CD4 比较 → 解出 "This is a fake flag"（decoy！）
└── 真载体：.data 0x41C000 处 dword 数组，每 dword 取低字节 XOR 0x07 → 释放 stage2 PE（0x15000 字节）
        ↓
stage2.exe（第二层）——真校验程序
└── 小型 VM（取指-译码-执行）→ **实际是魔改 SM4**：48 字节输入分 3 块，与 0x421018 的 12 dword 比较
```

## 二、第一层：识别 decoy + 提取内嵌 PE

> ✅ **v1.5.3+ 起这一步已被工具自动化**：`scanCryptoFingerprints` 的**载荷检测流水线**会直接扫文件字节、
> 定位编码存储的下一层载体，并在扫描结论里给出**可直接运行的提取脚本**（偏移/编码参数/长度全是自动推出来的）。
> 日志出现 `[算法扫描] 载荷命中：...` 即为此能力生效。
> 覆盖形态：单字节 XOR/ADD×stride、周期 XOR(2/3/4/8)、滚动 XOR/ADD、Base64/Hex 文本、ELF/DEX（含编码）、shellcode 序言。
> 下方的手工方法用于**理解原理 / 工具未覆盖的编码形态**（如双字节滚动、自定义码表）。

**通用检测原理（不依赖具体偏移）**：内嵌载荷常被**逐字节编码**后放进数据段，明文搜魔数**必然搜不到**。
利用类型魔数首两字节的**编码差与密钥无关**这一恒等式，可 O(n) 全文件枚举：
- **PE**：`buf[i] ^ buf[i+stride] == 0x17`（4d^5a）/ `(buf[i+stride]-buf[i]) & 0xff == 0x0d`（5a-4d）
- **ELF**：`0x7f ^ 0x45 = 0x3a` / `0x45 - 0x7f = 0xc6`
- **DEX**：`0x64 ^ 0x65 = 0x01` / `0x65 - 0x64 = 0x01`（两条判据重合，靠完整头校验区分）
- `stride` 取 `1 / 2 / 4`：覆盖字节数组、`uint16_t[]`、`uint32_t[]`（**只取低字节**）三种存放形态
- **验证靠结构而非巧合**：PE 走 `e_lfanew → PE\0\0 → 节表`；ELF 走 `e_shoff/e_shentsize/e_shnum`；
  DEX 走 `dex\n035\0 → file_size`（极小误报率）

⚠️ **`key=0` 的明文不算"内嵌载荷"**（偏移 0 + key 0 必须跳过）。否则每个正常 ELF/PE 都会把自己报成
"内嵌自己"，让 AI 对每道正常题都先去提取下一层——回归题集实测曾全员误报，这是必须守住的护栏。

**decoy 特征**（不要停在这里）：
- 静态校验表解出的内容是 `This is a fake flag` / `fake` / 提示性文字
- 题名/字符串暗示伪装（Disguise）
- 程序里有明显"加载器"特征（VirtualAlloc + 手工映射 / 大块 .data + 解码循环）
- ⚠️ **诱饵 flag 已由工具自动识别**（`isDecoyFlag`：fake/decoy/dummy/假flag…），不会再把"命中诱饵"报成 ✅

**提取器特征码**（照这个找）：
```c
n = *(DWORD*)0x470000;          // 输出长度（0x15000）
p = malloc(n);
for (i = 0; i < n; i++)
    p[i] = (*(DWORD*)(0x41C000 + i*4) ^ 0x07) & 0xff;   // 每 dword 取低字节 XOR 7
```

**Python 复现**：
```python
import pefile, struct
pe = pefile.PE(r'Disguise.exe')
data = pe.get_memory_mapped_image()          # 或 get_data(rva, size)
n = struct.unpack('<I', data[0x470000:0x470004])[0]
out = bytes(((struct.unpack('<I', data[0x41C000+i*4:0x41C004+i*4])[0]) ^ 7) & 0xff for i in range(n))
open('stage2.exe','wb').write(out)           # 首两字节应为 4D 5A (MZ)
```

## 三、第二层：VM 外壳 → 认出标准算法（核心）

**VM 外壳特征**：
```c
while (1) {
    op = code[pc];            // 取指：code 是 dword 数组
    switch (op) {             // 译码
        case 0: ...           // 初始化
        case 1..7: ...        // 算术（+= -= ^= 等）
        case 9/10/26: ...     // 条件跳转 / 循环标记（标志寄存器 + 跳转目标）
        case 16: goto end;    // 退出
    }
}
```
- 寄存器/状态空间 = 一大块内存（如 `dword_423A88[1010]`），S 盒/密钥/明文全放里面不同偏移
- 操作数是**相对偏移量**（`mem[code[pc+1]]`）

**不要逐条啃 26 个 handler** —— 直接列常量表对照标准算法：

| VM 里的东西 | 对照结论 |
|---|---|
| S 盒 256 字节，首字节 `0xD6` | **SM4**（AES 是 `0x63`） |
| 常量 `0xa3b1bac6 0x56aa3350 0x677d9197 0xb27022dc`（FK） | **SM4 铁证** |
| 轮常量表（CK）32 个 | SM4 密钥扩展必需 |
| 32 轮 + 轮函数 `A ^ B ^ C ^ rk` | SM4 分组结构 |
| 16 字节种子密钥 → 32 个轮密钥 | 对称分组密码密钥扩展 |

**Disguise 的实际情况**：VM 前半段是**轮密钥扩展**（16 字节 key 按大端拼 4 个 DWORD → 与 FK 异或 → 32 轮扩展），后半段是 **32 轮分组变换**；轮函数与标准 SM4 同构，但 **FK/CK/S 盒被换成自定义值**。

## 三·五、用工具扫描结果确认魔改算法（v1.5.3 新增，省预算关键）

工具在采集阶段会**直接读文件字节**扫算法指纹，并把结果注入到求解提示词**最顶部**
（`## ⚙️ 工具已确定性识别的算法指纹`），形如：

```
- 【SM4-FK】置信度 high  证据：命中 @0x422010  a3b1bac6 56aa3350 677d9197 b27022dc
           建议：SM4 系统参数 FK（铁证，出现即 SM4）
- 【CUSTOM-BLOCK-SBOX】置信度 medium  证据：@0x41EC30 起 256 字节为 0..255 双射表，首字节 8e
           建议：疑似自定义分组密码 S 盒（需核对轮结构与常量）
```

**怎么读这个结果（决定走哪条路）**：

| 扫描输出 | 含义 | 下一步 |
|---|---|---|
| `SM4-FK` 命中 + S 盒首字节 `D6` | 标准 SM4 | 直接 `sm4_ecb`/`sm4_cbc`，别手写 |
| `SM4-FK` 命中 + S 盒首字节 **≠** `D6` | **SM4 魔改变体** | 结构照抄标准 32 轮，FK/CK/S 盒换成题目内存里的表 |
| `自定义分组密码（已确认）high` + 256 项双射 S 盒 | **一定含分组密码**（常量被改） | 按"识别三问"核对轮结构 → 套标准框架手写；**不要**手撕 VM |
| 只有 256 双射表、无任何已知常量 | 自定义分组密码 | 先核对轮结构（32 轮 `X^X^X^rk` 还是 SubBytes 四步），再决定框架 |
| 无任何指纹 → `(未发现算法指纹)` | **本层是壳/加载器/decoy** | 去下一层（解出内嵌 PE / stage2）**再扫一次**，别在本层硬找算法 |

> ⚠️ **S 盒可能是"定长步长"数组**（本轮最关键的修复）：
> C 代码里 S 盒常写成 `unsigned int sbox[256]`，即使值域只有 0..255 也**占 4 字节/项**，
> 在文件里长这样：`8e 00 00 00  2f 00 00 00  03 00 00 00 …`（值在低字节，高 3 字节为 0）。
> 如果只按"连续 256 字节"找双射表，会**完全漏掉**它 —— Disguise 的自定义 S 盒 @0xd630 正是此形态，
> 这也是此前"AI 每次把 SM4 变体认成 AES 变体"的根因。扫描器现已同时扫 **stride=1 / 2 / 4** 三种形态。
> 自己写脚本找 S 盒时，务必三种步长都试。

**硬顺序约束（工具已写进提示词）**：出现 `confidence: high` 的算法判定时，
**必须先用该算法的标准解密框架（含魔改变体修法）完成验证**；
只有在标准路线确实全部失败（并说明尝试了什么、报错是什么）之后，**才允许**进入
"逐条 opcode 手撕 VM"的路线。**禁止无视判定直接开始啃 VM 字节码**。

> 实测教训：Disguise 的解法本来 10 分钟能出——扫描器在 stage2 里一眼命中 FK + 自定义 S 盒，
> 答案就是"魔改 SM4"。但在没有确定性识别前，AI 每次都往 AES 变体猜、反编译 13 个 handler、
> 烧掉 500+ 秒仍卡在"怎么写模拟器"。**先识别、再动手**是可复用的省预算习惯。

## 四、魔改标准算法的解密（照抄标准框架，换常量）

```python
# 结构 = SM4；常量来自题目；轮密钥逆序用；最后块内字节反序
def decrypt_block(ct_words, round_keys, sbox):
    state = list(ct_words)
    for i in range(32):
        t = state[(i+1)&3] ^ state[(i+2)&3] ^ state[(i+3)&3] ^ round_keys[31 - i]
        state[i & 3] ^= t_round(t, sbox)
    return [state[3], state[2], state[1], state[0]]   # ← 最后的字节反序，别漏
```

**三个必查的坑**：
1. **轮密钥逆序**（`rk[31-i]`）—— 加密正序、解密逆序
2. **块内字节反序**（`[3][2][1][0]`）—— 魔改题常加
3. **常量替换**（FK/CK/S 盒非标准）—— 不能用 gmssl 直接解

## 五、验证（块密码必做）

- 正向加密已知候选：`enc(candidate) == 密文` 成立才算对
- 多块独立（ECB 语义）：每 16 字节块单独解
- 别指望运行 stage2——Debug 版 PE 常缺 MSVCP140D 等 DLL，静态复现才是正路
