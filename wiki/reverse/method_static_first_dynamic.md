- 阶段 5 增量收敛：命中值 → 推出中间量 → 用工具离线复算 → 与运行值比对；不一致说明断点位置或栈帧偏移算错，先修假设再继续
- 阶段 6 收口：把动态拿到的常量/密钥/内存布局写回静态结论，用脚本正向复现一次，产出可复现的 VERIFY

- 一上来就 start + 随机单步 → 进程在系统 DLL、消息循环、库初始化里打转，几十轮下来零信息

- 在 GUI 程序里用 run_to 等校验函数 → 校验只在按钮回调里执行，启动后永远等不到（实测 8 轮 IP 全程停在系统 DLL）
- PIE 目标用静态地址下断点 → add_bpt 返回 False / 命中不了；必须用运行时重定位后的地址
- 目标启动即跑关键逻辑（无 sleep 窗口）→ 调试器还没下完断点它已经执行完了，表现为断点"设了却不命中"

# 静态先行、定向动态——动态调试的入场条件与函数锁定流程

> 核心判断：**动态调试不是探索手段，是取证手段。** 它回答的是"这个值运行时是多少"，
> 而不是"这段代码在干什么"——后者静态反编译更便宜、更可复现。

## 一、为什么必须先静态跑完数据

一次调试会话的固定成本很高：启动调试器、加载符号、处理反调试、把流程逼到目标位置。
如果此时还没锁定函数，这些成本会花在**无目的的漫游**上：

| 无底图就调试 | 有底图再调试 |
|---|---|
| 断在 `sub_401000`，不知道它读哪个参数 | 断点处直接 `[ebp-0x24]` = 输入缓冲区，一次读 32 字节 |
| 在消息循环里等校验函数 | 已知校验在按钮回调 → 先喂输入或改内存触发 |
| 单步 50 条看不出逻辑 | 静态已读懂逻辑，动态只要 3 个运行时值 |
| 结论是"我看到的"，无法复现 | 结论带地址/表达式/期望值，脚本可复算 |

## 二、入场条件（四条全满足才启动调试器）

> 一句话判据：**什么时候该动态调试？** 当且仅当你已经能写出"在哪个地址、读哪个表达式、
> 期望看到什么"——写不出来就是还不该调试。

1. **有函数清单**：知道程序里有哪些函数、哪些是候选（关键字符串交叉引用、常量表使用者、
   主流程调用链上只被调用一次的小函数）。
2. **每个候选函数有明确职责**：能用一句话说清它做什么（读输入 / 做变换 / 比对 / 解壳）。
3. **写得出调试假设**：对目标断点写清"命中后读什么表达式、期望看到什么、怎么判定通过"。
4. **有办法把执行流逼到那里**：入口断点 / 输入触发 / 定时触发 / 直接改 IP。

写不出第 3 条，说明静态还没读够——回到反编译，不要启动调试器。

## 三、阶段 0：用 MCP 把静态底图建起来

目标不是"看完整个程序"，而是**拿到够写假设的最小信息集**：

```
list_funcs                       → 函数清单（数量/命名/导出）
decompile(主入口)                 → 主流程骨架
decompile(候选1..3)              → 候选函数语义
xref(关键字符串 / 常量表地址)      → 谁在用这些数据
scan_crypto(文件路径)             → 算法族（AES/SM4/RC4/TEA/MD5 常量）
globals_by_address(常量地址)      → 常量表内容（S 盒 / K 表 / 密文块）
```

产出记录格式（后面调试直接照抄）：

```
候选 A: 0x4012d0  check_input(char* buf, int len)
        职责: 对输入做 XXTEA 加密后与 0x404060 的 32 字节比较
        要取: 入参 buf 指针、加密后缓冲区内容
候选 B: 0x403130  WinMain
        职责: 创建对话框，消息循环
        要取: 控件句柄（用于喂输入）
```

## 四、阶段 1：断点选址的三条优先级

| 优先级 | 选址 | 理由 |
|---|---|---|
| 高 | **变换函数的入口/出口** | 出入口各断一次，就能拿到输入原值与输出值，等于拿到整段映射 |
| 高 | **memcmp/strcmp/wcsncmp 的调用点** | 一眼看到"期望值 vs 实际值"，几乎等于拿到答案 |
| 中 | 解密循环内部 | 只在需要知道轮密钥/中间态时才断，粒度细但收益低 |
| 低 | 系统 API / CRT 初始化 | 噪声，除非在处理反调试或环境依赖 |
| 避免 | 消息循环、sleep、网络等待 | 断在这里等于没断 |

**一次命中的取数清单**（照着做，避免来回单步）：

- 通用寄存器（含 IP/SP）
- 函数参数（按调用约定：x64 `RCX/RDX/R8/R9`，x86 栈上 `[esp+4]...[esp+0x10]`，ARM64 `X0..X3`）
- 关键内存：入参指向的缓冲区、全局密文块、常量表
- 调用栈（判断是谁调用的，确认走的是哪条分支）

## 五、阶段 2：模式选择（本地 vs 远程，别用错）

| 目标 | 调试模式 | 要点 |
|---|---|---|
| PE（Windows） | 本地 win32 | 启动后停在入口，可直接单步 |
| ELF（Linux） | Kali 上 `dbgsrv/linux_server` | **不是 gdbserver**；调试器名 `linux`；SSH 里用 `setsid` 启动 |
| 32 位目标在 64 位宿主 | 本地 win32 | 窗口消息跨位数不可靠，优先改内存 |
| Android .so | 设备上 `android_server` + Frida | 见 `ctf-frida-dynamic` |

## 六、阶段 3：窗口期——最容易白费功夫的地方

"断点设了却不命中"（也常被描述为"断点设了不命中"）最常见的原因不是断点错，
而是**目标早就跑过去了**。
（同义说法：断点不生效、断点没反应、断点设了没用、断在系统 DLL、run_to 等不到。）

三类应对：

1. **入口先停**：先在入口/`main`/`WinMain` 下断点，`start` 后立刻命中，再从暂停态补下目标断点。
2. **制造睡眠窗口**：目标有 `sleep`/`getchar`/等输入行为时最理想——趁它停着把断点下完。
3. **启动后立刻 suspend**：远程模式 `start` 不会自动停在入口，必须主动 suspend 固定进程。

`continue`/`run_to` 是**异步投递**：命令返回时进程往往还在跑，必须确认真的暂停
（状态回到"已暂停"）才能单步或写内存，否则会得到一堆"失败"但其实只是状态没到。

## 七、阶段 4：动态取证的正确粒度

```
❌ 命中 → step → step → step → ... → step（30 次后仍不知道关键值）
✅ 命中 → 读寄存器 + 读 3 处关键内存 + 看调用栈 → 离线复算 → 只对不一致处再断一次
```

动态只用来回答静态答不出的问题：解出来的字符串是什么、展开后的密钥是什么、
真实分支走了哪边、缓冲区里实际写了多少字节。

## 八、阶段 5：增量收敛与自证

每拿到一个运行时值，立刻做一次**离线复算**：

```
运行时: 输入 "AAAA" → 变换后 3F 7A 91 ...
离线:   用自己的脚本对 "AAAA" 做同样变换 → 必须逐字节相等
```

不相等时按顺序排查：断点位置错（断在变换前后不同点）→ 栈帧偏移算错（`ebp`/`rsp` 相对位置）
→ 字节序/宽度错（`dword` vs `byte`）→ 调用约定错（参数根本不在你以为的寄存器里）。

## 九、特殊场景

### SMC（自修改代码）
静态看到的是**未解密的花朵/乱码**。正确顺序：先静态找到解密循环与目标节，
**在解密循环结束处下断点**，命中后把解密后的真实字节 dump 出来，
再对 dump 出来的字节重新静态分析。不要试图静态读 SMC 的密文段。

### 反调试
静态先识别反调试手段（`ptrace`、`IsDebuggerPresent`、`NtQueryInformationProcess`、
`TracerPid`、`rdtsc` 计时差、`int3` 扫描、异常处理链），再决定是 patch、hook 还是绕过。
动态里遇到"一附加就退出"，先回去看反调试在哪，而不是反复重试。

### GUI 程序
校验只在消息回调里执行，启动后阻塞在消息循环。两条路：
- 32 位目标：**先在读输入的指令下断点，命中后直接 `dbg_write` 改输入缓冲区**（跨位数窗口消息不可靠）
- 64 位目标：标准控件可 `gui_input` 喂输入并触发按钮

### 无交互的程序
看看有没有命令行参数、文件输入、环境变量、stdin 读取——这些才是把流程逼到校验点的开关。

## 十、Frida 场景同样适用

Android/JS 逆向里这条纪律一样成立，只是把"断点"换成"hook 点"：

1. 静态定位方法全名、参数类型、返回值形态（jadx / JEB）
2. 写清 hook 假设：在 `onEnter` 打印哪个参数、`onLeave` 打印哪个返回值
3. 再执行 `frida -U -f <pkg> -l hook.js`
4. 拿到的值同样要离线复算验证

## 十一、预算对照（实测经验）

| 做法 | 典型代价 |
|---|---|
| 无假设随机单步 | 30+ 次调用、仍无结论 |
| 有函数清单 + 目标断点 + 批量取数 | 3~6 次调用拿到全部运行时值 |
| 静态反编译读逻辑 | 1~2 次调用 |
| 离线复算验证 | 1 次脚本 |

结论：**静态能回答的，绝不用动态**；动态只用在那 10~20% 静态确实拿不到的值上。
