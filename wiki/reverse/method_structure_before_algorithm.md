# 结构先于算法

三道题（ELFStudy / qwb2026 firmware / license）表面上毫无关系：
一个是 PIE 可执行、一个是固件 + OTA 包、一个是静态链接的 license 校验。
但它们卡住的地方是**同一个**：**真正的校验逻辑不在你能直接看到的地方**。

## 一、三种"看不见"

| 藏法 | 表现 | 为什么静态工具看不到 |
|---|---|---|
| **段尾缝隙** | 反编译出一堆空函数 | 数据在 `p_filesz` 之外，任何按段/节遍历的工具都跳过；但内核按**页**映射 |
| **加密 blob** | `scan_crypto` 报零指纹 | 常量本身是密文，扫当然扫不到 |
| **单步异常流** | 指令被逐条解密、执行、再还原 | 任一时刻内存里都不存在完整明文代码 |

共同点：**"没看到"不代表"没有"**。这时该做的不是换算法、也不是硬猜，
而是**找结构上的不自洽**。

## 二、第一步永远是结构检测

### ELF：`elf_anomaly`

正常编译器产出的 ELF 元数据是自洽的。一旦有人要做加载期自修改，就必然留下痕迹：

```
DF_TEXTREL            → 要写代码段
RELASZ ≠ .rela.dyn+.rela.plt  → 遍历终点被挪动
COPY/RELATIVE 打 .dynsym      → 用加载器改写符号表项
STT_GNU_IFUNC + SHN_ABS       → 加载期会调用 st_value 处的 resolver
页尾缝隙有非零数据             → 藏在映射内但不属于任何段/节
addend 指向未覆盖区            → 引用了一块"藏"起来的数据
endbr64 + nop×N + ret        → 被掏空的函数，等着被改成跳板
```

**实现上有四个必须注意的点**（都踩过）：

1. 页尾**不能按整段平均**判。真实样本是「大片零 + 中间夹真数据」，
   整段非零比只有 13%，会漏。必须滑窗（128/32）找连续块再合并。
2. `.bss` 是 NOBITS，文件里**不占字节**。算进覆盖会让覆盖率超 100%，
   把真数据误判成"已被节覆盖"。
3. 节表本体（`e_shoff` 起 `e_shnum*entsize`）要算已覆盖——它是合法数据但不属于任何 section。
4. **只有 RELATIVE/COPY 的 addend 才有文件偏移语义**。PC32/GOTPCREL 的 addend 是
   指令内位移常量（常见 0x10/0x18），按文件偏移解释会大面积误报。

### 固件包：描述符 + 尾部标记

多段 OTA 把镜像拆散存放，靠描述符表拼回。三个坑：

- **步长未必 8 字节**：实测是 `(off, len, crc)` 三元组 = 12 字节
- **片段不连续**：直接哈希原始字节必然错，必须先按描述符拼
- **CRC 可能校验明文**：实测 OTA 存的是密文，但描述符 CRC 等于**明文**三段的 CRC32。
  这个观察直接证明了"密文 + 明文校验和"结构

尾部标记块（`<标记><u32 LE 长度><数据>`）是 flag/密钥最常待的地方。
长度字段是**小端**——按大端读会得到远超文件大小的值，可用这点快速判字节序。

## 三、第二步：把密文变成明文

`blob_decrypt` 的思路是**不做语义猜测，只做确定性比较**：

1. 穷举候选家族（链式 XOR / 滚动 XOR/ADD / 单字节）
2. 逐个试解
3. 用**可判读性**打分排序

打分的核心信号：

| kind | 主信号 | 为什么可信 |
|---|---|---|
| `code` | **capstone 指令覆盖率** | 错误密钥解出来会大量断在指令中间，覆盖率骤降 |
| `text` | 可打印比例 | |
| 通用 | 熵下降 + 零字节比例 | |

实测效果：ELFStudy 的 816 字节，正确答案得分 **103.97**，第二名只有 12.73。
解出的明文以 `90 90 90 90 f3 0f 1e fa 53 55 41 54 48 89 e5 48`
（nop×4 + endbr64 + push rbx/rbp/r12 + mov rbp,rsp）开头——一眼就是函数序言。

**链式 XOR 的确切定义**（别记反，它不是自逆的）：
```
key = 0
for i = N-1 downto 1:
    P[i] = C[i] ^ key
    key = (key + P[i]) & mask     # 累加的是明文
P[0] = C[0]                        # 索引 0 不变
```

## 四、第三步：代数结构别手推

license 题的校验是：

```
Y = Feistel3(X) ^ X
out = M · Y            # M 是 24×24 的 GF(2) 矩阵
要求 out == target
```

手推 24 行矩阵，任何一行抄错就全错且无从察觉。`arx_solve` 做两件事：

### 1. 从样本反解线性映射

给 ≥ n 组线性无关的 `(输入bit, 输出bit)`，高斯消元解出 M。
只用单位向量最稳。样本不足会明确报「秩不足」，**不会给假解**。

### 2. 三轮 Feistel 换元（把 2^64 降到 2^32）

这是**整道题最关键的思路**：

```
设 t = U ^ V ^ W
由正向关系可推出：
    g1(U) = t ^ yL
    g2(V) = t
    g3(W) = t ^ yR
⇒ 三个变量都用 t 表示
⇒ 判据：g1⁻¹(t^yL) ^ g2⁻¹(t) ^ g3⁻¹(t^yR) ^ t == 0
⇒ 只需枚举 32 位 t
命中后：L = W ^ yL,  R = U
```

**必须先验证这三条等式**：拿一组已知 (L,R) 正向算出 U/V/W，检查。
不成立说明 `g` 的定义搞错了——`g⁻¹(z) = P⁻¹·(S⁻¹(Q⁻¹·z)) ^ k`，
**k 在最外层**，写反了永远找不到解。

### 3. 用 C，不用 Python

| 实现 | 2^32 耗时 |
|---|---|
| C + `-O3 -march=native` | **18 秒** |
| Python + numpy 向量化 | ~40 分钟 |
| JS | ~30 分钟 |

工具直接生成**自包含 C 源码**（参数内联），`gcc` 一下就能跑。

### 4. 多候选是正常的

实测同一组参数命中 **8 个候选**。三轮 Feistel 的输出不唯一，
**必须**把每个候选拼成完整输入喂回原程序验证。不要看到第一个就交。

## 五、贯穿三题的一条原则

**把"能不能解"变成"数据够不够"。**

- 页面缝隙 → 有数据就有偏移，有偏移就能取
- 加密 blob → 有密文就有明文（只要算法在候选集里），能用覆盖率判定
- Feistel → 有公式就能换元降维，降完就是算力问题
- OTA → 有描述符就能拼，有摘要就能对账

每一步都不需要"灵光一现"，只需要**把结构摆清楚 + 用确定性指标判定**。
这道题真正的门槛不是数学，是**先意识到"没看到"≠"没有"**。
